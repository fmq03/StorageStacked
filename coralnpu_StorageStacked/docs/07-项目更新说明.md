# 项目更新说明

[返回文档目录](README.md)。本篇仅展示项目更新内容，以及修改后已有仿真结果的对比和研究。
本次根据保存的实际记录整理，没有新增仿真；benchmark 明细见 [验证说明](08-验证说明.md)。

## 1. 项目更新内容

| 部分           | 已完成更新                                                                                  | 当前保留的约束                                                                         |
| -------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| CPU / gem5     | 在原有核数、频率、容量和 TLB 配置上，增加 x86_64/aarch64 切换及 L1I/L1D/L2 相联度、延迟配置 | 使用 TimingSimpleCPU；ARM SE 的 TLB 条目数是对象配置，未据此建模硬件 TLB 命中/缺失时序 |
| GPU / Vortex   | 保留执行规模、频率、缓存容量和 L2 开关，增加 L1I/L1D/L2 相联度及访问周期配置                | 结果来自 SimX；GPU 程序仍执行 RV32                                                     |
| NPU / CoralNPU | 按 user 配置生成 RTL、构建 Verilator 模型及设备库，开放 L0 开关和三组 TCM 预设              | ITCM/DTCM 为 8/32、512/512、1024/1024 KiB；RVV/浮点及现有 BF16 构建组合固定            |
| 结果管理       | 按配置、日志、程序、原始记录、检查和网页分类，提供各 benchmark 的结果索引和报告             | 原始运行证据与文档汇总对应保存，历史失败不计作当前成功                                 |
| 编辑器与文档   | 刷新当前模型索引及新增 Chisel/Python 跳转，验证说明按 benchmark 分类保存                    | 导航通过不代表功能仿真或综合通过                                                       |

### 1.2 CoralNPU：新增 L0 和 TCM 配置字段

更新前，npu 节点只有时钟参数。以下片段直接对应旧配置：

```json
{
  "npu": {
    "clock_mhz": 500
  }
}
```

更新后，同一节点为：

```json
{
  "npu": {
    "clock_mhz": 500,
    "fetch_l0_enabled": false,
    "itcm_kib": 8,
    "dtcm_kib": 32
  }
}
```

两段只展示 npu 节点，完整配置的其他节点仍需保留。

| 字段                     | 更新前 config.json       | 更新后当前值 | 新增的配置能力                       |
| ------------------------ | ------------------------ | ------------ | ------------------------------------ |
| `npu.clock_mhz`        | 500                      | 500          | 原有设备时钟配置保持不变             |
| `npu.fetch_l0_enabled` | 无字段，用户配置不能选择 | false        | 可设为 true/false，选择开启或关闭 L0 |
| `npu.itcm_kib`         | 无字段，由 RTL 构建决定  | 8            | 与 dtcm_kib 配对选择 ITCM 容量       |
| `npu.dtcm_kib`         | 无字段，由 RTL 构建决定  | 32           | 与 itcm_kib 配对选择 DTCM 容量       |

允许的 ITCM/DTCM 配对为 8/32、512/512、1024/1024 KiB。
例如选择 L0 开启和 512/512 KiB，设置 fetch_l0_enabled=true、itcm_kib=512、dtcm_kib=512，
再通过原运行入口构建、加载对应模型。缺少三个新字段的旧配置会补入 false、8、32。
这里的 TCM 是保留的容量参数；当前 benchmark 集合为 SMOKE、TinyLLM、AXI burst。

### 1.3 Vortex CPU：新增 ISA 与缓存字段

更新前没有以下字段，ISA 和缓存相联度/阶段周期由既有平台实现决定；更新后可从 host 节点选择。

| 新字段                      | 更新前的配置及行为            | 更新后当前值 | 配置含义                                   |
| --------------------------- | ----------------------------- | ------------ | ------------------------------------------ |
| `host.isa`                | 无字段，主机运行路径为 x86_64 | "x86_64"     | 可选择 "x86_64" 或 "aarch64"               |
| `host.l1i_ways`           | 无字段，L1I 固定 8 路         | 8            | L1I 相联度                                 |
| `host.l1i_latency_cycles` | 无字段，L1I 各阶段固定 1 周期 | 1            | 同时设置 L1I 的 tag/data/response 阶段周期 |
| `host.l1d_ways`           | 无字段，L1D 固定 8 路         | 8            | L1D 相联度                                 |
| `host.l1d_latency_cycles` | 无字段，L1D 各阶段固定 1 周期 | 1            | 同时设置 L1D 的 tag/data/response 阶段周期 |
| `host.l2_ways`            | 无字段，L2 固定 16 路         | 16           | L2 相联度                                  |
| `host.l2_latency_cycles`  | 无字段，L2 各阶段固定 10 周期 | 10           | 同时设置 L2 的 tag/data/response 阶段周期  |

延迟单位是 CPU 周期，各阶段周期不等于整笔访存总延迟。
当前示例保留 x86_64 默认主机，选择 ARM 时需主动将 host.isa 改为 "aarch64"。
主机核数、频率、缓存容量和 TLB 条目数沿用原配置值。

### 1.4 Vortex GPU：新增缓存字段

更新前相联度和访问周期由模型默认规则决定；更新后可从 gpu 节点显式配置。

| 新字段                     | 更新前的配置及行为     | 更新后当前值 | 配置含义                               |
| -------------------------- | ---------------------- | ------------ | -------------------------------------- |
| `gpu.l1i_ways`           | 无字段，模型默认 4 路  | 4            | L1I 相联度                             |
| `gpu.l1i_latency_cycles` | 无字段，周期随容量推导 | "auto"       | 沿用容量关联规则，也可指定合法整数周期 |
| `gpu.l1d_ways`           | 无字段，模型默认 4 路  | 4            | L1D 相联度                             |
| `gpu.l1d_latency_cycles` | 无字段，周期随容量推导 | "auto"       | 沿用容量关联规则，也可指定合法整数周期 |
| `gpu.l2_ways`            | 无字段，模型默认 8 路  | 8            | L2 相联度                              |
| `gpu.l2_latency_cycles`  | 无字段，周期随容量推导 | "auto"       | 沿用容量关联规则，也可指定合法整数周期 |

延迟单位是 GPU 周期。当前容量下，"auto" 解析为 L1I/L1D/L2 的 2/2/4 周期。
默认 L2 仍关闭；L2 的新参数在启用该层后参与对应缓存行为。

## 2. 修改后仿真结果对比和研究

### 2.1 对比口径

以下比较新增配置能力在不同设置下的实际行为：NPU 比较同批 L0 关闭/开启，
Vortex 比较同批默认/修改后的缓存参数。旧版本跨日期的周期只作历史记录，不直接计算更新收益。
周期变化率采用 `(对比周期 - 基线周期) / 基线周期 × 100%`；负值表示周期减少。
CPU/GPU 组合实验与 NPU RTL 仿真的模型、运行软件和统计范围不同，不作跨平台优劣排名。

### 2.2 NPU：L0 开关的影响

数据来自 2026-10-21 的 l0-20261021-adapter 矩阵；同一行保持负载、时钟、TCM 和外部参数一致，
仅改变 L0 开关。SMOKE/TinyLLM 的三组 TCM 得到相同的对应周期。

| Benchmark | 适用 TCM（KiB）          | L0 关闭周期 | L0 开启周期 | 周期差 | 周期变化 | 输出            |
| --------- | ------------------------ | ----------: | ----------: | -----: | -------: | --------------- |
| SMOKE     | 8/32、512/512、1024/1024 |         308 |         307 |     -1 |  -0.325% | 42              |
| TinyLLM   | 8/32、512/512、1024/1024 |      222187 |      223375 |  +1188 |  +0.535% | blu / [4,10,15] |

两类负载输出均正确，但开启 L0 的周期收益不同。SMOKE 仅减少 1 周期，
TinyLLM 增加 1188 周期，不能把“开放 L0”写成统一性能提升。
TinyLLM 8/32 KiB 的推理至最后 token 时间为 332208 → 334560 ns（增加约 0.708%）；
其中 prefill 至首 token 增加 1762 ns，两个 decode 间隔合计增加 590 ns。
这是阶段标记时间；整段 NPU 周期还包含其他执行部分，两种百分比的统计窗口不同。
两种状态均为 4196 笔外部事务、42 次 RVV 线性层调用，数值误差也一致；
现有记录没有取指命中率、未命中停顿或退休阻塞的完整计数，不能据周期差断言具体瓶颈。

### 2.3 NPU：TCM 扩容的作用

512/512 和 1024/1024 KiB 在相同 L0 状态下：SMOKE 均为 308/307 周期，
TinyLLM 均为 222187/223375 周期（斜线依次对应关/开）。
当前工作负载没有呈现从 512/512 扩到 1024/1024 的周期收益。
三组容量预设均能够运行上述 SMOKE/TinyLLM；相同 L0 状态下周期一致。
没有测量把同一工作集从外存搬入不同 TCM 的成对实验，因此不能据此推导一般性的外存流量或速度收益。

### 2.4 CPU/GPU：缓存参数组合实验

采用 2026-10-19 的同批八组记录，容量、核数和对应业务输入保持不变。

| 配置     | CPU L1I/L1D/L2 路数 | CPU 各层阶段周期 | GPU 路数  | GPU 周期  | GPU L2 |
| -------- | ------------------- | ---------------- | --------- | --------- | ------ |
| 默认基线 | 8 / 8 / 16          | 1 / 1 / 10       | 4 / 4 / 8 | 2 / 2 / 4 | 关     |
| 修改组合 | 4 / 4 / 8           | 2 / 2 / 12       | 2 / 2 / 4 | 3 / 4 / 7 | 开     |

CPU 各层阶段周期同时设置 tag/data/response。下表的周期来自 GPU 的 SimX 记录。

| Benchmark | 主机 ISA | 默认 GPU 周期 | 修改组合 GPU 周期 | 周期变化 | 输出 |
| --------- | -------- | ------------: | ----------------: | -------: | ---- |
| SMOKE     | x86_64   |           862 |              1255 | +45.592% | 42   |
| SMOKE     | aarch64  |           862 |              1259 | +46.056% | 42   |
| TinyLLM   | x86_64   |        226411 |            219379 |  -3.106% | blu  |
| TinyLLM   | aarch64  |        226839 |            218285 |  -3.771% | blu  |

所有场景均有 4 个实际活跃 CPU，数值及链路验证通过。
修改组合使 SMOKE 周期增加约 45.6%～46.1%，TinyLLM 周期减少约 3.1%～3.8%，体现负载敏感性。
实验同时改变了 CPU/GPU 相联度、访问周期及 GPU L2 开关；
可以确认组合配置影响执行，但无法把差值单独归因于某一级缓存或某一个参数。
两种 ISA 下产生正确结果说明适配功能成立，也不足以支持一般性的 ISA 性能优劣判断。
完整批次数据见 [Vortex 验证说明](../../vortex_StorageStacked/docs/07-验证说明.md)。

### 2.5 AXI burst：拆拍与压力条件

固定负载和每次 16 字节原生请求不变。1/2/4/8 拍的其他配置一致：
L0 关闭、TCM 8/32 KiB、outstanding=16、stalls=true、replay=false。

| 每请求拍数 | 每拍字节 | NPU 周期 | 相对 1 拍的周期变化 |
| ---------: | -------: | -------: | ------------------: |
|          1 |       16 |     1703 |             +0.000% |
|          2 |        8 |     1766 |             +3.699% |
|          4 |        4 |     1893 |            +11.157% |
|          8 |        2 |     2198 |            +29.066% |

该负载的 8 拍配置比 1 拍增加约 29.1% 周期，写/读数据拍从 21/10 增至 168/80；
原生请求数量仍为 31，输出校验和均为 0xb91b80ea，说明拍数变化保持了功能结果。
本适配器是把固定请求拆成更多窄拍，不能将更大 burst_beats 直接理解为更高有效带宽。
16 拍场景为 3013 周期，但它另外启用 replay=true 并把 outstanding 降到 1；
此结果作为正确性和压力覆盖记录，不用于单独量化拍数对性能的影响。

### 2.6 已得到的结论与后续研究

现有记录支持：新增参数进入实际模型；指定 benchmark 的数值结果保持正确；
配置对周期的影响依赖负载，容量扩展和性能提升应分别评价。
默认完整回归及模型矩阵均通过；各配置的逐场景报告、阶段时间、反压计数和错误拒绝结果
按 benchmark 保存在 [验证说明](08-验证说明.md) 中。

下一步可研究以下项目，均尚未由本篇数据完成：

- 固定其他参数，逐一改变 L1I、L1D、L2 相联度、周期和 L2 开关，分离单参数贡献。
- 增加不同指令工作集、分支行为及数据局部性的负载，并记录 L0 命中、填充和停顿计数。
- 在相同程序与外存布局下研究 TCM 工作集放置及容量边界，观察实际外部事务变化。
- 固定 outstanding、反压和重放条件做 burst 对比，分别统计有效字节吞吐和请求响应延迟。

本篇数据属于指定功能负载的仿真结果，不延伸为完整大模型精度、GPU RTL 综合、FPGA/芯片实现或全负载性能保证。
