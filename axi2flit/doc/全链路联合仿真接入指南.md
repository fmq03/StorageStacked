# 全链路联合仿真接入指南

本文说明项目现有接口，以及 gem5、Vortex 和 Ramulator 的接入方案。当前工程已经连接 AXI 激励、协议桥、UCIe 行为链路、存储响应端和简单内存；**尚未实现本文提出的 gem5、Vortex、Ramulator 适配器**。文中的拟新增模块和接入步骤属于实施方案。

核心建议：保留桥的 AXI 逐拍接口和存储侧突发事务接口，在边界增加适配器。主机模型负责产生访问，AXI 适配器负责握手，链路负责传输，存储后端负责数据与访问时序。无需把整个系统改成信号级，也无需把整个系统改成 TLM。

交接时先看[SoC 侧接口对接表](SoC侧接口对接表.md)和[存储侧接口对接表](存储侧接口对接表.md)第 1～3 节，再共同确定[联仿交接约定](#11-联仿交接约定)。这两份接口表描述当前字段、字节布局与完成顺序；本文负责模型选择、适配和统一调度方案。

| 内容                                                  | 当前状态         | 接入方如何使用                                          |
| ----------------------------------------------------- | ---------------- | ------------------------------------------------------- |
| AXI 五通道、UCIe、Target、整突发内存 FIFO             | 已实现           | 按当前端口和类型绑定                                    |
| `FullLinkTb` 与简单内存、AXI 自检和波形             | 已实现的测试顶层 | 参考装配，拆出所需驱动/监视逻辑                         |
| 独立`FullLinkSystem`、主机/存储适配器、trace 回放器 | 尚未实现         | 根据所选模型开发，当前没有对应 make 目标                |
| 存储侧隐藏 RP/USER 等字段的公共接口                   | 可选设计方案     | 不替代现有`SimpleMemRequest/Response`，实施前统一约定 |

本文中 burst 指一笔突发，beat 指其中一个数据拍，outstanding 指已接受但尚未完成的请求，RP 指资源平面。父请求/子事务只描述适配层确实发生拆分时的关系，并非当前接口必备字段。外部项目的链接说明接入依据，具体 API 和构建方式须按交付所选提交核对，不代表本工程已验证任意版本组合。

## 1. 当前工程实际在仿真什么

```text
AXI BFM ⇄ Axi2Flit ⇄ UcieAouAdapter ⇄ UcieLink ⇄ AouTarget ⇄ SimpleBurstMemory
         AXI 信号      帧握手             帧 FIFO             突发事务 FIFO
```

| 边界                   | 当前接口                                            | 一次交付的粒度                       | 接受与完成                                                                    |
| ---------------------- | --------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------- |
| SoC ↔ 桥              | `sc_in/sc_out` 端口绑定 `sc_signal`，AXI 五通道 | 地址、一个数据拍或写响应             | 上升沿`VALID && READY` 接受；B 握手或最后一个 R 拍握手表示对应 AXI 事务结束 |
| 桥 ↔ Adapter          | `FlitTransfer` 信号及独立 `ready`               | 一帧                                 | 上升沿握手，阻塞时保持帧内容                                                  |
| Adapter/Target ↔ UCIe | `sc_fifo<FdiFlit>`                                | 一个含 250 字节项目帧内容的 FDI 事务 | FIFO 成功写入是交付，链路传输需要仿真时间                                     |
| Target ↔ 内存         | `sc_fifo<SimpleMemRequest/Response>`              | 一整笔 AXI 突发                      | 请求入队是接受，响应入队才表达后端定义的完成                                  |

桥和 Target 由时钟推进；UCIe 使用事件和延迟描述训练、传输、反馈及重放；简单内存一次处理一笔突发并等待服务时间。因此，**当前工程本身已经是不同粒度、不同时间推进方式的联合行为仿真**，不是全链路逐根信号的 RTL 仿真，也没有提供标准 TLM-2.0 socket。

`sc_fifo` 中传递 C++ 事务对象，可以称为事务级建模，但不等于已经实现 TLM-2.0 协议。`sc_signal` 只说明通信载体，是否逐周期、周期内如何更新，取决于模块进程及调度规则。

现有完整接线和运行说明见 [UCIe 全链路使用说明](UCIe全链路仿真计划与使用.md)；字段及顺序约束见[设计文档](../systemc/doc/design.md)和[字节格式与接口](../systemc/doc/wire_contract.md)。

## 2. 链路对外暴露的接口

### 2.1 SoC 侧：桥是 AXI 从机

主机需要驱动 AW、W、AR，并接收 B、R。下面方向均相对 `Axi2Flit`，实际声明见 [axi2flit.h](../systemc/include/axi2flit.h) 和 [axi_if.h](../systemc/include/axi_if.h)。

逐字段类型、实际范围、窄访问示例、AW/W 配对及采样规则以[SoC 侧接口对接表](SoC侧接口对接表.md)为交接入口。

| 通道 | 桥输入                  | 桥输出                | 主要内容                           |
| ---- | ----------------------- | --------------------- | ---------------------------------- |
| AW   | `aw_valid`、`aw_ch` | `aw_ready`          | 写地址、ID、LEN、SIZE、BURST、属性 |
| W    | `w_valid`、`w_ch`   | `w_ready`           | DATA、STRB、LAST、USER             |
| B    | `b_ready`             | `b_valid`、`b_ch` | ID、RESP、USER                     |
| AR   | `ar_valid`、`ar_ch` | `ar_ready`          | 读地址、ID、LEN、SIZE、BURST、属性 |
| R    | `r_ready`             | `r_valid`、`r_ch` | ID、DATA、RESP、LAST、USER         |
| 控制 | `clk`、`rst_n`      | —                    | 时钟、低有效复位                   |

它在 SystemC 中把同一通道的字段打包成结构体，并非每个字段都单独声明端口；语义仍是 AXI 五通道握手。连接 RTL 时需要把离散端口打包/拆包。**有效性以独立的 `*_valid/*_ready` 信号为准，不以通道结构体中的同名状态字段为准。**

地址是 64 位字节地址，ID 为 10 位，USER 为 16 位，数据宽度编译选择 256/512/1024 位。数据数组下标 0 对应最低字节 lane；写选通数组每项的零/非零表示该字节是否有效。

支持按 SIZE 对齐、不跨 4KB 的 INCR 突发，SIZE 不超过数据总线宽度，LEN 表示拍数减一，最多 256 拍。全宽访问还受 4KB 限制；不支持的主机请求须由适配器拆分或明确拒绝。独占、原子和缓存一致性事务不能直接当作普通读写转换。

每个上升沿，`VALID && READY` 表示交付一次；`VALID && !READY` 时发送方必须保持 VALID 和载荷。AW 与 W 分别握手，不能要求二者同拍成功；W 没有 ID，适配器必须维持写数据与写地址的对应顺序。

资源平面 RP 由 `QOS % rp_count` 选择。相同方向、相同 ID 的未完成事务应保持在同一 RP，并按序返回；读与写之间没有隐含全局顺序。验证写后读依赖时，先等待 B，再发起依赖读。

### 2.2 存储侧：Target 发起事务，后端提供存储服务

实际类型定义见 [simple_mem_if.h](../systemc/include/simple_mem_if.h)。

当前字段与可选接口方案分别见[存储侧接口对接表](存储侧接口对接表.md)。首轮连接使用已有类型，后端若需要其他格式，在包装层转换；不要求先实施新的公共接口。

```text
AouTarget.mem_req  ── sc_fifo<SimpleMemRequest> ──→ 后端.request
AouTarget.mem_rsp  ←─ sc_fifo<SimpleMemResponse> ── 后端.response

SimpleMemRequest
  write                    读/写方向
  rp                       资源平面
  address                  AXI 地址及 ID、LEN、SIZE、属性
  write_beats[]            写数据、逐字节 strobe、USER；读请求为空

SimpleMemResponse
  write、rp、id             匹配原请求
  resp、user               写响应状态与 USER
  read_beats[]             每拍 DATA、RESP、USER；写响应为空
```

读响应必须包含原请求的全部 `LEN+1` 拍。后端必须保持同方向、同 RP、同 ID 的完成顺序；不同 ID 可以在遵守数据依赖的前提下乱序完成。后端可自行使用唯一内部序号跟踪请求，但不能仅凭地址匹配回调，因为同一地址可以被重复访问。

当前 `SimpleBurstMemory` 保存真实字节数据，串行处理请求，默认服务时间为 `20ns + 2ns × 拍数`。测试地址窗口为 `0x1234567800000000` 起的 128KiB；这只是测试配置，接入真实主机时应重新配置可达地址范围和容量。

存储器只提供从机功能时，存储侧保留一个 `AouTarget` 即可。它负责解包请求、访问后端、打包 B/R 响应，也发送必要的 credit 消息；不需要一个主动发起主机访存的对称请求端。将来若增加存储侧 DMA、回调主机访问或一致性功能，才需要相应的请求发起能力。

### 2.3 Adapter 为什么存在

`UcieAouAdapter` 负责将桥的逐拍帧握手转换成 UCIe 模型的帧 FIFO，并提供有限暂存及背压。它不是每个联合仿真模型都必须携带的模块。

当前桥与 `UcieLink` 之间需要这个适配器；Target 自身已经使用相同的 FDI FIFO，所以直接接入链路。以后是否保留 Adapter，取决于新模型的接口：接口一致就直接连接，接口不同才需要相应转换。TLM→AXI 适配器和 Adapter 分处两个边界，不能相互替代。

## 3. gem5 提供什么，如何接入

### 3.1 原生接口是 Packet/Port，TLM 是可选桥接层

gem5 原生内存系统通过端口传递 Packet。Timing 访问建模排队、请求/响应和重试；Atomic 访问同步返回估计延迟；Functional 访问用于装载、调试等功能性访问。这里的 Atomic 仿真模式与 CPU 的原子指令不是同一概念。[gem5 内存系统说明](https://www.gem5.org/documentation/general_docs/memory_system/)

gem5 确实提供 SystemC/TLM 联仿支持。在外部 SystemC 集成示例中，`Gem5SlaveTransactor` 向 SystemC 暴露 **TLM initiator socket**，把 gem5 发起的访问送到外部设备；`Gem5SimControl` 负责 gem5 事件队列与集成。不要因为名称含 Slave 就把它误接成 TLM target。[gem5 官方 TLM 示例](https://raw.githubusercontent.com/gem5/gem5/stable/util/tlm/README)

另一条官方路线是内建 SystemC 支持下的 `Gem5ToTlmBridge`，其 gem5 侧是 ResponsePort，TLM 侧是 initiator socket。这与外部 SystemC 集成属于不同的构建/调度路线，应选择一条，不能同时链接两套 SystemC 内核。[桥接类声明](https://raw.githubusercontent.com/gem5/gem5/stable/src/systemc/tlm_bridge/TlmBridge.py)

### 3.2 本工程建议的拓扑

```text
gem5 CPU / Cache / LLC
          ⇅ gem5 Timing Packet/Port
官方 gem5 → TLM 桥（TLM initiator）
          ⇅ TLM-2.0 请求/响应
拟新增 TlmToAxiMaster（上游 TLM target，下游 AXI master）
          ⇅ 当前 AXI 五通道信号
Axi2Flit ⇄ Adapter ⇄ UcieLink ⇄ AouTarget ⇄ 存储后端
```

本工程已使用外部 SystemC 库，建议首先复用 gem5 的外部 SystemC 示例组织顶层。接入点选择 LLC 后的普通内存访问边界，并为选定物理地址窗口路由到该链路。直接替换一致性网络中的端口，还需要额外的一致性协议设计，当前 AXI 桥不承担这项职责。

`TlmToAxiMaster` 至少需要完成下列转换：

| 上游内容                       | 适配器职责                                                     |
| ------------------------------ | -------------------------------------------------------------- |
| READ/WRITE、字节地址、数据长度 | 生成合法的 AR 或 AW/W；必要时拆分多个 AXI 突发                 |
| 数据与 byte enable             | 按 AXI 字节 lane 放置 DATA/STRB，读回时提取有效字节            |
| streaming width、特殊命令/扩展 | 检查实际语义，支持的转换，不支持的明确报错                     |
| 上游事务身份                   | 分配最多 10 位的可用 AXI ID，记录父事务和子事务映射            |
| QoS、请求属性                  | 使用明确的默认值或 TLM 扩展；不能假设通用载荷自带所有 AXI 字段 |
| B 和全部 R 拍                  | 合并数据及错误状态，对原始事务只完成一次                       |

例如，一个对齐的 64B TLM 请求，在 256 位 AXI 上可以是 2 拍，在 512 位上可以是 1 拍，在 1024 位上可以是 1 拍 64B 窄访问。**一个 TLM 事务并不必然对应一个 AXI 数据拍。** Socket 模板的总线宽度与载荷长度也不是同一个限制，绑定时应匹配 socket 类型，再独立处理 AXI 位宽转换。

实施时还应满足：

- 有限请求队列、ID 池、响应缓存；收满后把背压传回上游。不要用无限队列掩盖桥的压力。
- 载荷、数据缓冲和扩展存活到协议允许释放的时刻；异步处理不能保留已失效的调用栈指针。
- 将 Functional/调试装载接到同一份后端数据存储；这条不计时路径不能意外成为正常 Timing 访问的旁路。第一阶段在计时运行前完成镜像装载；若支持运行中 Functional 访问，还需处理在途写缓存和响应缓存的数据一致性。测量区域关闭会绕过链路的 DMI。
- 保留 gem5 Timing 请求拒绝后的 retry 机制和响应背压。若直接写 Packet→AXI 桥而不用 TLM，仍然需要实现这些机制。
- 先用简单 Timing 主机验证功能，再使用能产生足够并发请求的 CPU/缓存配置评估性能。低并发主机跑不满链路，不等于桥的吞吐能力不足。

## 4. Vortex 提供什么，如何接入

### 4.1 RTL 路线：优先接 `Vortex_axi`

Vortex 的 RTL 原生存储端口是自定义请求/响应信号；官方还提供 `Vortex_axi`，把它转换为 AXI 五通道，可配置数据宽度、地址宽度、ID 宽度和 bank 数。它不是原生 TLM socket。[原生 RTL 顶层](https://raw.githubusercontent.com/vortexgpgpu/vortex/master/hw/rtl/Vortex.sv)、[AXI 包装层](https://raw.githubusercontent.com/vortexgpgpu/vortex/master/hw/rtl/Vortex_axi.sv)

```text
Vortex_axi RTL
      ⇅ Verilator 生成的 SystemC 模块端口
拟新增 AxiSignalShim（字段打包/拆包、位宽和复位适配）
      ⇅ 当前 AXI 信号
Axi2Flit ⇄ Adapter ⇄ UcieLink ⇄ AouTarget ⇄ 存储后端
```

RTL 可以与 SystemC 一起仿真。建议先用 Verilator 的 `--sc` 路线，把生成的模块与当前模型放在一个 SystemC 内核中；端口 C++ 类型以生成的头文件为准。Verilator 内部使用编译后的模型，不意味着 RTL 每根内部导线都会成为一个 `sc_signal`。[Verilator SystemC 示例](https://verilator.org/guide/latest/example_sc.html)、[模块连接说明](https://verilator.org/guide/latest/connecting.html)

第一阶段建议单 bank、相同数据位宽、相同 AXI 时钟。连接时重点处理：

- `Vortex_axi` 的高有效 reset 与本工程 `rst_n` 的极性转换；保留 DCR、start、busy 等启动和控制通路。
- AXI 离散信号与通道结构体之间的组合打包。若使用寄存器适配，明确新增的周期；不要因双方采样顺序偶然多插一拍。
- ID 超过 10 位时分配/回收映射，不能直接截断。多 bank 时另需仲裁、响应路由及 ID 命名空间设计。
- 无 USER 的端口按约定填零；LOCK 等不同宽度字段验证取值后转换，不静默截断特殊操作。
- 使用 AXI 包装层输出的字节地址；若接原生接口，必须按其配置恢复块地址和 bank 信息，不能直接当作字节地址。

所核对的 `VX_mem_to_axi` 实现令 `AWLEN/ARLEN=0`、`WLAST=1`，QoS 为零；它发出单拍 AXI 访问，默认会落到本桥 RP0。它还在本地接受写响应，原生写通路不提供与 AXI B 等价的上游完成握手。因此长突发、多 RP 和响应背压仍需保留独立 BFM 测试；软件结束也不能直接等同于链路全部写入完成。[AXI 转换实现](https://raw.githubusercontent.com/vortexgpgpu/vortex/master/hw/rtl/libs/VX_axi_adapter.sv)

需要写后读依赖或最终结果检查时，应核对所选 Vortex 配置的 fence、缓存和写缓冲行为，并在测试顶层完成 drain：等待必要的缓存写回、AXI 响应、链路及后端未完成事务归零。仅观察 `busy` 拉低不足以替代这项检查。

### 4.2 SimX 路线：自有 C++ 仿真接口，需要另外适配

SimX 是另一条仿真路线。其处理器代码用内部内存请求/响应通道连接缓存和 Memory，并通过仿真平台的 `tick()` 推进；它不自动提供 TLM-2.0 socket，也不是 `Vortex_axi` 的 RTL 端口。[SimX 处理器实现](https://raw.githubusercontent.com/vortexgpgpu/vortex/master/sim/simx/processor.cpp)

接入时应在所选配置的末级缓存/内存边界新增 `SimXToAxi`，转换请求与完成通知，并让 SimX 的周期推进服从联合仿真时间。还要核对实际数据路径：Vortex 有独立的 RAM 数据读写及镜像装载实现，不能仅替换一个内存延迟回调，却仍让真实读值绕过链路从另一份 RAM 获取。[RAM 数据接口](https://raw.githubusercontent.com/vortexgpgpu/vortex/master/sim/common/mem.h)

如果目标是验证真实 AXI 握手和观察接口波形，优先选 RTL 路线；如果目标偏向程序负载与架构性能，可再接 SimX。两者产生的访问序列和时序精度应分别说明，不能因运行同一个程序就视为等价。

## 5. Ramulator 如何接到存储侧

### 5.1 用库接口替换简单内存

```text
AouTarget
    ⇅ SimpleMemRequest / SimpleMemResponse FIFO
拟新增 RamulatorBackend（SystemC 包装层）
    ├─ 地址检查、突发拆分、依赖与完成管理
    ├─ ByteDataStore：保存真实数据、处理字节选通和镜像装载
    └─ Ramulator C++ 库：提交请求、拒绝重试、DRAM tick、完成回调
```

本方案以所核对的 `ramulator2` 主分支接口为参考，其 README 当前标识为 **Ramulator 2.1**，库模式提供外部请求入口、内存时钟推进及配置接口；不能直接套用其他版本的构建脚本和函数签名。[Ramulator 官方仓库](https://github.com/CMU-SAFARI/ramulator2)

该请求类型包含地址、方向、大小、来源和回调等信息，没有本项目需要的 DATA/WSTRB 载荷。因此 Ramulator 用来决定访问时序，包装层还要保存实际字节数据。`source_id` 是来源标识，不是能直接代替 AXI ID 的唯一事务号。[Ramulator 请求定义](https://raw.githubusercontent.com/CMU-SAFARI/ramulator2/main/src/ramulator/base/request.h)

已经存在 gem5→Ramulator 的包装示例，但把它直接接在 gem5 内存端会绕过本工程。这里需要的是 **Target→RamulatorBackend**，同时保留中间的 AXI 桥与 UCIe 链路。[官方 gem5 包装示例](https://raw.githubusercontent.com/CMU-SAFARI/ramulator2/main/resources/gem5_wrappers/ramulator2_base.cc)

### 5.2 请求拆分和数据管理

1. 检查整笔地址、SIZE、掩码和窗口，避免非法突发产生部分写副作用。物理地址减去配置基址得到后端偏移，不能直接截断高位。所有 RP 默认访问同一存储空间。
2. 为父突发分配内部唯一序号及有限数据/完成缓存，再读取请求 FIFO。当前 Target 默认最多容纳 8 笔后端 outstanding，后端自己的容量也应明确。
3. 在同一父请求内部按 DRAM 事务边界拆分或合并有效字节范围，记录每个子请求对应的 AXI 拍和字节。首轮不合并不同父请求，避免改变上游的完成、错误及依赖边界。事务大小读取配置，不硬编码为 64B；使用 `get_tx_bytes()` 与 `get_tCK()` 等接口取得模型参数。[内存系统接口](https://raw.githubusercontent.com/CMU-SAFARI/ramulator2/main/src/ramulator/memory_system/i_memory_system.h)
4. 提交失败则保留该子请求，在后续内存时钟重试；提交成功就不能重复提交。接口的接受与完成是两件事。[外部请求入口](https://raw.githubusercontent.com/CMU-SAFARI/ramulator2/main/src/ramulator/frontend/impl/external.cpp)
5. 在各子请求满足完成条件后组装整笔响应；同方向、同 RP、同 ID 的父事务按接收顺序释放。

例如，1024 位、16 拍全宽突发包含 2048B；若所选 DRAM 配置每事务 64B 且起始地址相应对齐，需要 32 个子请求。反过来，同一个 64B 区间内的两个 32B AXI 拍可按既定策略合并。不能无条件按“一个 AXI 拍等于一个 DRAM 请求”计数。

WSTRB 控制字节存储的更新，不能因 DRAM 模型只看到读写类型就覆盖整个总线拍。全零 WSTRB 应返回正确的逻辑完成，并明确是否省略 DRAM 请求；稀疏写如何占用 DRAM 事务也应成为配置和统计口径的一部分。

后端必须统一镜像装载、Functional/调试访问和正常读写的数据来源。处理重叠地址时，第一阶段可用保守的依赖串行化，后续再实现写缓冲转发。读子请求在定义的可见时刻保存数据快照，避免最后合并响应时读到随后写入的新值。桥不同方向之间的依赖仍需由主机的同步语义保证，后端不能凭空恢复上游没有传达的顺序。

### 5.3 特别注意写完成与回调

所核对的 `ControllerBase` 在普通写最终命令发出时调用写回调；对已经缓冲的同地址写，可能在 `send()` 内合并并立即调用回调。该回调并不等价于完整 DRAM 写数据/恢复时序结束。[控制器实现](https://raw.githubusercontent.com/CMU-SAFARI/ramulator2/main/src/ramulator/controller/controller_base.cpp)

因此建议第一阶段明确定义：写响应表示“全部子请求达到所选模型的写完成通知条件，且后端数据可见”，不要把 B 的时刻解释为物理介质写入完成。若选择接收入队就提前返回写响应，须另外实现待写数据转发和 drain，并单独标注这种完成语义。

适配器要在调用提交函数**之前**建立回调上下文，处理同步回调重入；回调只记录完成事件，不执行可能阻塞的 FIFO 写，也不在其中调用 `wait()` 或递归推进仿真。切换版本或控制器后，必须验证读写通知条件，不能假设所有实现都会以相同方式发出写回调。

响应 FIFO 满时暂存完成事务，并停止接受超出容量的新请求。为已接受请求预留完成缓存，才能让压力经 FIFO、Target 和链路最终传回 AXI。

### 5.4 当前整笔突发接口的性能边界

当前 Target 收齐写突发后才交给后端；读响应也要包含全部数据拍，Target 才能开始返回它们。Ramulator 内部即使逐周期运行，外部仍有这两个整笔等待点。

这足以进行功能闭环和明确该接口条件下的系统性能测试，但长突发首拍延迟会受最慢子请求影响，无法直接表达“部分 DRAM 数据已回来，马上向 SoC 发送第一个 R 拍”。若研究关键字优先返回、流式长突发或细粒度流水，下一步需把存储接口扩展成请求头、写数据流、逐拍读响应，并增加事务序号、拍序号、LAST 和有限重排缓存。

## 6. TLM 如何握手，是否会太粗

应分别考虑三个问题：用什么接口通信、一次传多少数据、如何描述时间。三者可以独立选择。

| 建模形式         | 交付机制                      | 时间描述             | 对本项目的用途                  |
| ---------------- | ----------------------------- | -------------------- | ------------------------------- |
| AXI 信号         | 时钟边沿 VALID/READY          | 每周期采样           | 验证桥握手、背压和波形          |
| 当前事务 FIFO    | 成功读写及有限容量            | 模块等待时间或时钟   | 帧传输、完整突发存储请求        |
| TLM LT           | 通常用`b_transport`         | 粗粒度延迟或时间标注 | 早期功能集成、简化性能估计      |
| TLM AT           | `nb_transport_fw/bw` 和阶段 | 阶段事件、排队和重叠 | 外部主机与 AXI 适配器的并发交互 |
| Ramulator 库接口 | 请求接受/拒绝和回调           | DRAM 周期推进        | 控制器排队和 DRAM 时序          |

TLM-2.0 基础非阻塞协议的典型阶段是 `BEGIN_REQ → END_REQ → BEGIN_RESP → END_RESP`，也允许协议规定的阶段简化。它不要求额外添加 VALID/READY 信号；接受、响应、载荷生命周期由函数返回值、阶段和标注时间共同表达。[TLM-2.0 语言参考手册](https://accellera.org/images/downloads/standards/systemc/TLM_2_0_LRM.pdf)

下面是拟新增 TLM→AXI 适配器的一种合法设计思路，箭头间隔不是固定周期：

```text
上游主机           TLM→AXI 适配器                    AXI 桥
 BEGIN_REQ ───────→ 保留请求上下文
          ←─────── END_REQ：请求已进入有限队列
                   AW/W 或 AR ─────────────────────→ 逐拍握手
                   ……允许其他事务进入队列……
                   B 或全部 R ←───────────────────── 完成
          ←─────── BEGIN_RESP：返回状态和读数据
 END_RESP ───────→ 释放响应及载荷上下文
```

`END_REQ` 在这个设计中表示适配器接受排队，不代表 AXI AW 已握手，更不代表内存已经完成。发送方在协议允许的新请求阶段可以继续发起事务，因此采用事务接口不意味着一次只能处理一笔。

队列满时，适配器可以保留一个尚未结束请求阶段的事务并延后 `END_REQ`，遵守请求阶段互斥规则。返回 `TLM_ACCEPTED` 表示接收了这次协议调用，且没有通过返回路径更新阶段；它不能当作“数据已经完成”或通用 FIFO 的布尔成功。基础协议也没有一个可随意返回的 `TLM_RETRY`。响应阶段同样要处理上游接收时刻和生命周期，不能提前复用缓冲。

非阻塞回调中不等待时间，而把事件交给 PEQ/调度进程在阶段的生效时间处理。LT 的阻塞调用和 `sc_fifo::read/write` 可以让当前 SystemC 线程等待，但不会让整个 SystemC 内核停摆；循环重试却不让出调度权，才会阻止其他模块推进。

对于本工程，保留 AXI 逐拍边界是有价值的，因为待测对象正是该接口的转换行为。主机到适配器可按 cache line 或突发传一个 TLM 事务，再由适配器展开为真实时钟握手；无需让 gem5 在每个周期调用一次 TLM。TLM AT 的阶段也不自动等于 RTL 周期精确，其精度取决于适配器是否正确建模容量、调度和响应时间。

## 7. 逐周期与事件驱动模型如何统一时间

### 7.1 一套权威仿真时间，各模型按自己的事件推进

建议复用官方集成调度，以 SystemC 时间作为当前工程对外的统一时间轴：AXI 时钟、UCIe 事件、Ramulator 时钟和主机事件都映射到这条轴。外部 gem5 路线由其 SystemC 集成层维护事件同步；不要在旁边单独启动一个无限运行的 `gem5 simulate()` 循环。

AXI 默认周期 2ns。Ramulator 的周期从配置读取，可能与 AXI 不成整数倍；UCIe 的发送延迟来自链路配置，不需要模拟为每个物理比特一根信号。按各自最早到期事件推进即可，不能用“每个 AXI 周期只 tick 一次 Ramulator”代替时钟比例。

一个仅用于说明边界采样的例子：TLM 请求在 10.3ns 生效，若 AXI 的有效采样边沿为 10、12、14ns，那么最早可安排到 12ns 边沿交付。以后内存若在 35.625ns 通知完成，Target 可以在其后符合接口调度约定的时钟边沿看到响应。传输、队列和信用等待还要另行计入，不能把这些示意时刻当作全链路延迟预测。

### 7.2 必须固定的调度约定

- **时间单位与精度**：现有全链路采用 1fs 时间分辨率。将 gem5 Tick 按实际频率转换，将 Ramulator tCK 转为统一时间，避免浮点累计漂移或把事件舍入到允许时间之前。
- **同一时刻的顺序**：明确时钟采样、信号更新、FIFO 可见性和回调处理的 delta-cycle 关系；同时间戳不保证消费方一定在本次边沿看到刚写入的值。
- **每个模型只推进一次**：Ramulator 后端定时调用内存系统 `tick()`；不要同时运行它的独立主循环。没有模型支持的快进机制时，空闲期也须维护刷新等周期行为。
- **只计算一次延迟**：TLM 标注延迟和实际等待必须一致，不能对同一段延迟既等待又再次累计到下一事件。
- **不越过外部反馈**：主机不能先跑到很远的未来，再把旧时间的访存塞回 SystemC。先使用严格同步；扩大时间量子前验证对依赖、背压和中断的影响。
- **协调启动和退出**：沿用链路激活后的统一复位释放；退出前排空主机、适配器、AXI、链路重放和后端事务。当前链路不支持有在途事务时的单端热复位。

因此，周期精确模型与周期近似模型**可以联合仿真**。统一的是时间和交互契约，不是要求它们都在每一拍执行一次。联合后能保证到何种精度，取决于各模块和边界是否保留了研究所需的行为；把精确 DRAM 模型接进来，不会自动使事件驱动 UCIe 和整突发存储接口变成 RTL。

## 9. 如何证明功能、时序和性能正确

### 9.1 保留已有的功能与波形入口

在项目根目录执行：

```bash
make full-link-all
make full-link-negative
make full-link-wave
```

这些命令验证当前 BFM＋UCIe＋简单内存路径，**不会自动运行尚未接入的外部模型**。`full-link-all` 包含三种位宽、RP 配置以及压力/重放场景；判据和产物见[验证文档](../systemc/doc/verification.md)及[波形使用说明](UCIe全链路仿真计划与使用.md)。

新主机顶层应复用 AXI trace 和监视器，继续生成五通道 VCD 与事务 CSV。观察波形时以时钟边沿 `VALID && READY` 计数；检查背压期间载荷稳定、W/R 拍数与 LAST、B/R 的 ID 和返回数据。AXI 波形证明的是该边界的实际握手，端到端数据正确性仍需独立参考模型或程序判据。

### 9.2 新适配器必须补充的测试

| 测试                                       | 要发现的问题                           |
| ------------------------------------------ | -------------------------------------- |
| 单拍、突发、窄访问、稀疏及全零选通         | lane 映射、字节覆盖、拆分与合并错误    |
| 跨 4KB 或超长上游请求                      | 是否合法拆分、父事务是否只完成一次     |
| 同 ID 多笔、不同 ID 乱序、多 RP            | ID 冲突、错误配对和顺序丢失            |
| 请求拒绝重试、TLM 阶段延迟、响应长时间背压 | 丢包、重复提交、无限缓冲和死锁         |
| Ramulator 即时回调、延迟回调、重复地址     | 未建立上下文就收到完成、错误回调配对   |
| 写完成后读、部分写覆盖、装载后读、调试访问 | 数据旁路、旧值/未来值、未实现的依赖    |
| 非整数时钟比及不同初相                     | 提前完成、漏 tick、重复 tick、边沿竞态 |
| 主机完成但后端仍有在途写                   | 提前退出造成“程序通过、内存尚未完成” |

建议记录统一父事务序号，以及 gem5 Packet/SimX tag、AXI ID、RP、后端子请求序号的映射。每笔记录主机发起、AXI 接受、Target 提交、内存接受/完成、AXI 返回和主机接收的时间。父事务数、AXI 拍数、链路帧数和 DRAM 子请求数本来就不同，应通过映射核对守恒，而不是要求四个计数相等。

这些关联编号由顶层或适配器维护，用于调试与聚合；不是要求每个模型的请求接口都增加父事务和子事务字段。上游请求因 AXI 限制拆成多个 burst，与一个 burst 因后端限制拆成多个内存访问，是两个不同边界的拆分，应分别记录。

### 9.3 性能结论应明确测量边界

当前 `perf_report.txt` 来自简化链路下的桥性能测试，不是 gem5/Vortex＋UCIe＋Ramulator 的持续带宽报告。全链路功能通过也不等于系统性能满足要求。

接入后分别报告主机可见延迟、有效读写带宽、桥及链路流量、后端排队与 DRAM 统计。区分有效字节、总线字节和物理传输字节；区分被模拟系统的时间与运行仿真所耗的墙钟时间。性能门槛应同时固定工作负载、读写比、突发长度、并发数、地址分布和时钟配置。

定位瓶颈时先检查主机是否有足够 outstanding，再检查桥/Target 容量、UCIe 服务能力和内存排队。Vortex 单拍流量、gem5 cache line 流量和长突发 BFM 的封装开销不同，不能直接拿同一个带宽数作等价比较。当前 Target 的整突发等待点也应单独报告；若它影响目标指标，再实施逐拍存储接口。

## 10. 使用 gem5 trace 离线驱动链路

### 10.1 可行，但需要回放器生成 AXI 信号

可以先运行 gem5 记录访存，再用文件驱动本工程。这是离线流量回放，适合桥的回归和给定负载下的链路评估；当前尚未实现文件解析与回放入口。

```text
gem5 运行并记录选定边界的访存
                 ↓ 文件
转换工具 → 请求 trace → 拟新增 TraceAxiMaster
                                      ⇅ 实际 AXI 握手
                       Axi2Flit ⇄ UCIe ⇄ Target ⇄ 存储后端
                                      ↓
                           响应记录、检查报告、VCD
```

桥本身仍然接 AXI 信号，不直接读取文件。回放器承担主机职责：解析记录、调度请求、生成 AW/W/AR、保持背压时的载荷，并接收 B/R。离线路线不强制需要 TLM。

gem5 通常先在自身配置的内存系统中运行并生成记录。本次链路回放得到的响应不会自动改变那次已经完成的 CPU 执行。即使把响应输出成文件，也不等于建立了在线反馈；若要求 CPU 根据当前链路延迟或读值继续运行，应使用前述在线桥接。

### 10.2 trace 是访问记录，不一定是 AXI，更不等于机器指令

gem5 有多种 trace。Packet trace 可以用 protobuf 保存时间、命令、地址、大小及可选属性，并用官方脚本解码成文本；该脚本按可选字段输出不同列，不能无条件按固定列数解析。[Packet trace 解码器](https://gem5.googlesource.com/public/gem5/+/master/util/decode_packet_trace.py)

例如，读访问记录表达“在某个时刻请求地址 A 开始的 64B”，不代表一条完整的 CPU load 指令。记录点若在缓存之后，流量还受缓存命中、缺失、预取及写回影响；接本桥时应选择与预期 SoC 内存出口对应的记录位置。普通 Packet 命令和属性需要筛选或转换，不能把所有非读命令都当作写。

这种访问记录没有自动提供 AWLEN、AWSIZE、WSTRB、逐拍时序等完整 AXI 信息。所列 Packet trace 字段也不包含实际写数据或预期读数据，需要扩展记录或另外提供。Elastic Trace 则增加了指令依赖和计算延迟，适合依赖驱动的 TraceCPU 回放，仍不等于现成的 AXI 文件。[gem5 TraceCPU 与格式说明](https://www.gem5.org/documentation/general_docs/cpu_models/TraceCPU)

建议区分三种粒度：

| 文件内容                     | 回放工作                    | 用途                       |
| ---------------------------- | --------------------------- | -------------------------- |
| 读写操作、地址、字节数、时间 | 选择 AXI 拍宽并拆分事务     | 接入普通访存流量           |
| AXI 突发属性、数据与选通     | 按协议生成各通道握手        | 本工程推荐的可移植激励格式 |
| 每周期信号值/变化            | 处理与当前 DUT 反馈是否一致 | 波形分析或限定条件的复现   |

不建议把旧波形中固定时刻的 VALID 脉冲原样重放给不同延迟的系统。新的 READY 可能不同，回放器必须保持信号直到握手。DUT 驱动的 READY、B/R 数据不能当作主机激励强行驱动。

### 10.3 建议的输入格式示例

以下 CSV 是**拟议项目格式**，不是 gem5 默认格式，也不是当前已支持的输入语法。每行表示一笔 AXI 突发：

```csv
seq,earliest_ns,op,addr,beat_bytes,beats,axi_id,data_hex,byte_en,after_seq
1,0,W,0x1234567800000000,4,2,1,1122334455667788,ff,-
2,20,R,0x1234567800000000,4,2,2,-,-,1
```

约定如下：

- 第一笔向地址窗口起点写入 8B，以两个 4B 拍传输；第二笔读取同一区间，最早在 20ns 发起，并等待第 1 笔的 B 完成。时间原点取链路启动并释放复位后。
- `beats=2` 转换为 AXI `LEN=1`，`beat_bytes=4` 转换为 `SIZE=2`；示例限定 INCR，其他属性采用明确默认值。不要把 beat_bytes 直接赋给 AXI SIZE。
- `data_hex` 按地址递增排列，最低地址的字节是 `0x11`；`byte_en` 是十六进制逻辑字节掩码，第 0 位对应最低地址。示例 `ff` 使 8B 全部有效。回放器再按总线宽度和地址映射为各拍 WDATA/WSTRB。
- `seq` 是全局唯一记录号，`axi_id` 是可复用的 AXI 协议 ID。响应按在途队列映射回 seq，不能只用 AXI ID 当全局唯一编号。
- 请求头元数据还应固定格式版本、时间单位、位宽、记录位置、地址映射和内存初始化方式。完整格式可扩展 QoS、USER、预期响应及多项依赖。

`earliest_ns` 是最早允许发起时间，不是保证握手时间。到期后仍须等待依赖、ID/队列容量和真实 READY；同时记录计划时间与实际接受时间。多个独立请求可以重叠，不能默认每行都等上一行完成，否则会把并发流量串行化。

如果原始 trace 缺少数据，可以选择固定种子生成写数据并配独立字节参考模型，验证本链路的数据传输；这验证的是合成数据下的链路功能，不能宣称复现了原 gem5 程序的数据语义。若要对照原始程序的读值，则需记录写载荷、字节使能、必要的依赖、预期读值，以及记录起点对应的内存状态。

### 10.4 响应如何输出和检查

真实响应仍沿链路返回 AXI B/R，由回放器接收。响应文件只是观察记录，不是响应传输协议。建议按成功握手记录 `seq/channel/id/beat/last/resp/data/handshake_time`，另外生成父事务的首拍/末拍延迟、数据比较和超时结果。

当前测试已有 CSV 列：

```text
time_ns,case,channel,id,address,beat,last,resp,data_hex,strb_bits
```

它记录各通道真实握手；W/R 的 data_hex 按总线高 lane 到低 lane 输出，与上述拟议输入的地址递增字节顺序不同，转换时必须明确处理。现有 CSV 不含全部突发属性，也没有独立 seq，因此不能直接视为完备的可回放请求文件。实现位置见 [tb_full_link.cpp](../systemc/tb/tb_full_link.cpp)。

自动检查仍应使用独立参考状态，而不是把 DUT 输出的响应文件当成正确答案。纯地址流量可以测量请求数、背压、延迟和带宽；数据正确性需要确定的初值、写载荷及可判定的访问顺序。

### 10.5 性能解释边界

固定时间戳 trace 保留了原运行条件下的访问流量；链路延迟变化后，真实 CPU 的依赖等待、并发程度甚至后续路径可能改变，简单文件回放不会自动重建这些变化。即使回放器遵守 AXI 背压，也不能据此直接得到新系统的 CPU IPC 或程序运行时间。

第一阶段可以使用有限 outstanding、可配置时间缩放和显式依赖的事务回放器，测量给定负载下的链路行为；若要让请求调度随依赖完成而调整，可评估 Elastic Trace/TraceCPU 路线；若需要程序根据真实读值继续执行，则采用在线 gem5 联合仿真。

当前命令行没有通用的地址窗口、AXI 时钟或任意后端选择参数。更换这些内容需要配置新顶层或修改相应测试配置，不能假设增加一个 make 变量就生效。`--stress` 只是预设的 FIFO/延迟/背压组合，不是独立的内存时钟配置。

### 11.3 启动、运行和退出

1. 在创建 SystemC 对象前设置时间分辨率，构造并绑定全部模块；初始化主机请求 VALID、响应 READY、内存数据和计数上下文。
2. 启动时保持桥、Adapter、Target 复位，待链路 Active 后在约定相位释放。原 BFM 在下降沿驱动、上升沿监视，可作为首次集成的采样约定。
3. 正常访存必须实际经过 AXI 和链路。请求接收入队、后端完成、B/R 握手分别计时；不要把入队当作端到端完成。
4. 主机结束后等待已提交事务完成、必要的缓存写回和全部适配器队列排空。保持内存和链路推进以排出剩余响应与重放，随后停止；不能只凭 CPU 退出或 Target 空闲判断整个系统结束。

### 11.4 分阶段验收

| 阶段              | 最小验证                                                   | 输出                                  |
| ----------------- | ---------------------------------------------------------- | ------------------------------------- |
| 现有环境          | `make preflight`、`make full-link-all`；负向记分板检查 | 构建/运行配置及最终通过日志           |

| 原 BFM + 新存储   | 掩码、地址边界、错误、后端拒绝/乱序、整突发聚合            | 请求/响应映射、数据比较、队列排空结果 |
| 新主机 + 新存储   | 程序或 trace 工作负载、完整退出检查                        | 从主机请求到最终响应的计数和延迟关联  |
