## 1、写事务与平均延迟模型

### 1.1 平均写延迟的定义和计算公式

当前 `avg_write_latency` 是 **DRAM transaction 从 Controller 成功接收到完成的平均周期数**：

```text
单事务写延迟 = completion_cycle - arrival_cycle

avg_write_latency_ticks
  = total_write_latency / completed_writes

avg_write_latency_ns
  = avg_write_latency_ticks × tick_duration_ps / 1000
```


### 1.2 起点、终点与统计累计

请求被 Controller 成功接收时执行：

```cpp
req.arrival = clk_;
```

对应 [`src/controller/controller.cpp:158`](src/controller/controller.cpp:158)。



请求完成时，`complete_pending()` 将 `completion - arrival` 累加到 `total_write_latency`，并增加 `completed_writes`，见 [`src/controller/controller.cpp:686`](src/controller/controller.cpp:686) 和 [`src/controller/controller.cpp:740`](src/controller/controller.cpp:740)；平均值的定义见 [`include/hbm_sim/stats/stats.hpp:267`](include/hbm_sim/stats/stats.hpp:267)，tick 转 ns 见 [`src/stats/result.cpp:118`](src/stats/result.cpp:118)。

### 1.3 一次写事务

```text
Frontend 注入 → Controller 写队列 → 调度/写排空 → 必要时 PRE、ACT
→ 等待 Timing、刷新与总线资源 → WR/WRA → PHY/数据路径完成
→ TransactionResponse → 必要时汇聚为 HostResponse
```

影响项包括：`write_buffer_size` 与注入速率造成的排队，写高/低水位触发的 write-drain，row hit/miss/conflict，`nRCDWR`、`nCWL`、`nBL`、`nWR`、`nRP` 等 Timing，读写总线换向，refresh/RFM，以及 PHY FIFO/数据流水线。response queue 满会延后向上层交付，但统计仍用记录的 `completion - arrival`，不能直接说它增加了该延迟数值。写模式切换见 [`src/controller/controller.cpp:1307`](src/controller/controller.cpp:1307)，Timing 约束见 [`src/dram/spec.cpp`](src/dram/spec.cpp)。因此不能把平均写延迟等同于 `nCWL`。

**WR 与 WRA**：WR 后行保持打开；WRA 带 auto-precharge，关闭行必须等写数据、burst 和 write recovery 满足。项目在 WRA 完成时间上加 `nCWL+nBL+nWR` gate，见 [`src/controller/controller.cpp:1743`](src/controller/controller.cpp:1743)。

ACT、PRE 等前置命令不会结束写请求。请求一直留在队列或 active buffer，直到真正发出终端数据命令 WR/WRA：

```cpp
done_req.issued_cycle = clk_;
```

对应 [`src/controller/controller.cpp:1714`](src/controller/controller.cpp:1714)。

所以：

```text
issued_cycle - arrival_cycle
```

主要反映 Controller 排队、PRE/ACT、Timing、刷新和总线竞争；

```text
completion_cycle - issued_cycle
```

主要反映写数据路径和项目定义的完成点。

### 1.4 Direct 与 Behavioral 下的写事务

Direct 与 Behavioral 的完成定义并不相同；比较两种模式时要连同该口径一起看。

**Direct PHY**：

普通 WR 在 Direct 路径中默认于发出后一拍完成：

```cpp
done_req.completion = clk_ + 1;
```

见 [`src/controller/controller.cpp:1735`](src/controller/controller.cpp:1735)。这是一种行为级 acknowledgement，不表示真实 DRAM 单元在一拍内完成全部内部恢复。

WRA 带自动预充。它的完成点还必须等待：

```text
nCWL + nBL + nWR
```

代码取原完成点与该 gate 的最大值，见 [`src/controller/controller.cpp:1743`](src/controller/controller.cpp:1743)。这避免 WRA 在写数据、burst 和 write recovery 完成前就关闭物理 row buffer。

**Behavioral PHY**：接收 WR/WRA 后，写数据槽的 ready cycle 为：

```text
issued_cycle
+ timing_delay(dfi_write_latency_nck 或 nCWL
               + write_data_pipeline_cycles)
```

见 [`src/dram/mem_phy.cpp:208`](src/dram/mem_phy.cpp:208)。ready 后才真正写入 `MemoryImage` 并生成 PHY completion，见 [`src/dram/mem_phy.cpp:249`](src/dram/mem_phy.cpp:249) 和 [`src/dram/mem_phy.cpp:297`](src/dram/mem_phy.cpp:297)。

Controller 的 `complete_pending()` 会等待这一 completion，并以 PHY 返回的 completion cycle 为最终事实，见 [`src/controller/controller.cpp:699`](src/controller/controller.cpp:699)。

## 2、热模型与功耗模型的架构讲解

### 2.1 整体数据流

```text
Controller 发出命令
→ apply_storage_command_event()
→ MemoryImage::record_command_event()
→ command_energy_pj() 计算事件能量
→ 分类累计 ACT/PRE/RD/WR/REF/RFM/control 能量
→ physical_address() 得到 Stack/Layer/Tile/Thermal cell
→ apply_thermal_event()
→ 冷却、升温、横向/纵向耦合
→ 输出功耗统计和 thermal map
```

入口见 [`src/controller/controller.cpp:975`](src/controller/controller.cpp:975)，功耗/热共同入口见 [`src/core/data.cpp:1402`](src/core/data.cpp:1402)。

### 2.2 功耗模型

功耗采用“每条命令事件能量”抽象。`command_energy_pj()` 根据命令选择能量：

- ACT/ACT1/ACT2 → activate energy；
- PRE/PREpb/PREab → precharge energy；
- RD/RDA/CAS_RD → read energy；
- WR/WRA/CAS_WR → write energy；
- REFab/REFpb/REFdb → refresh energy；
- RFM → RFM energy；
- 其他命令 → control energy。

实现见 [`src/core/data.cpp:295`](src/core/data.cpp:295)。

项目支持两种参数来源：

1. `configured_pj`：配置直接给每命令 pJ；
2. `dramsim3_idd`：借鉴 DRAMsim3/IDD 电流差分形式，用 VDD、IDD、命令持续时间和器件数推导事件能量，见 [`src/core/data.cpp:370`](src/core/data.cpp:370)。

最终能量乘 `power_scale`，并累计到总能量和分类能量，见 [`src/core/data.cpp:1412`](src/core/data.cpp:1412)。这不是直接调用 DRAMsim3，也不是厂家校准后的绝对功耗模型。

Self-Refresh 驻留已按 DRAMsim3 的 IDD6 电流法计能：`VDD × IDD6x × 器件数 × 驻留时间`，SREFEN/SREFEX 的命令能量仍单独计入 control 类。驻留能量作为背景能量送入现有热网格；普通 active/precharge standby 等背景功耗不因此自动补齐。

### 2.3 热模型

命令能量通过 `apply_thermal_event()` 注入对应 thermal cell：

1. 根据当前周期与 `last_cycle` 的差计算冷却；
2. 温度向 ambient 按 `cooling_per_cycle` 衰减；
3. 增加 `energy_pj × rise_c_per_pj`；
4. 向同层四个相邻 cell 做 lateral coupling；
5. 向上下层做 vertical/TSV coupling；
6. 更新峰值和热点坐标。

冷却见 [`src/core/data.cpp:1239`](src/core/data.cpp:1239)，邻居耦合见 [`src/core/data.cpp:1276`](src/core/data.cpp:1276)，热事件见 [`src/core/data.cpp:1366`](src/core/data.cpp:1366)。

纵向耦合会根据 thermal cell 面积、TSV 半径/数量、硅和铜导热系数调整，见 [`src/core/data.cpp:1250`](src/core/data.cpp:1250)。

### 2.4 输出含义

- `power_energy_pJ`：所有已记录命令事件能量总和；
- 分类能量：按命令类别拆分；
- `thermal_peak_temp_C`：运行中已实例化 thermal cells 的最高温度；
- `thermal_avg_temp_C`：查询时刻已实例化稀疏节点的空间平均，不是整个未触达 die 的平均，也不是时间平均；
- thermal map：每个 cell 的最终温度、累计能量和事件数。

## 3、cmd和dfi的validation逻辑

### 3.1 两者检查对象不同

```text
Command Validation：IssuedCommand 是否满足 DRAM 状态和 Timing
DFI Validation：IssuedCommand 是否被正确转换为 DFI command/data events
```

它们都不是重新运行一遍 Controller 调度，而是对仿真产生的结构化轨迹进行重放检查。CLI 调用位置分别是 [`src/cli/main.cpp:2221`](src/cli/main.cpp:2221) 和 [`src/cli/main.cpp:2234`](src/cli/main.cpp:2234)。

### 3.2 Command Validation

Validator 按 Stack 分组，避免不同 Stack 的同 ID/同周期事件混淆，入口见 [`src/validation/validator.cpp:820`](src/validation/validator.cpp:820)。每个 Stack 内按 trace 顺序维护独立的 Bank/Channel 状态和 Timing 历史。

主要检查：

- Bank 是否 Closed/Activating/Opened；
- RD/WR 是否命中已打开 Row；
- PRE、ACT、refresh、RFM 的状态是否合法；
- same/different Bank、BG、PC、Rank、Channel 的 Timing；
- tFAW 滑动窗口；
- HBM Row/Column bus 和边沿配对；
- LPDDR ACT1/ACT2 配对；
- WCK readiness；
- PDE/PDX、SREFEN/SREFEX 状态。

状态检查核心在 [`src/validation/validator.cpp:355`](src/validation/validator.cpp:355)，Timing 重放在 [`src/validation/validator.cpp:553`](src/validation/validator.cpp:553)。约束不是一个单独 cfg 文件，而来自：

```text
DramSpec Timing 数值
+ src/dram/spec.cpp 构建的 TimingConstraint 表
+ validator.cpp 的协议状态规则
```

### 3.3 DFI Validation

DFI 生成器先把每条 issued command 转成一条 `COMMAND` event；RD/RDA 再生成 `READ_DATA` beats，WR/WRA 生成 `WRITE_DATA` beats。入口见 [`src/validation/dfi.cpp:215`](src/validation/dfi.cpp:215)。

验证器检查：

1. 每条 issued command 是否恰有一条 COMMAND event；
2. DFI 中是否有无来源的孤立事件；
3. cycle、issued cycle、bus、地址和 decoded location 是否一致；
4. `ceil(payload_bytes/beat_bytes)` 是否等于实际 beat 数；
5. beat index、周期、地址递增是否正确；
6. 读写信号字段是否互斥且完整；
7. payload、初始化 mask、write mask 是否一致；
8. 有 expected payload 时，读数据是否匹配。

入口见 [`src/validation/dfi.cpp:307`](src/validation/dfi.cpp:307)，command 一一对应检查见 [`src/validation/dfi.cpp:428`](src/validation/dfi.cpp:428)，data beat 检查见 [`src/validation/dfi.cpp:455`](src/validation/dfi.cpp:455)。

### 3.4 PASS 证明

PASS 能证明轨迹满足当前检查器中已实现的规则，不能单独证明：

- 覆盖全部 JEDEC 条款；
- DFI 完整信号级合规；
- 与真实厂家器件一致；
- 检查器与生成器没有共享相同理解错误。

因此还需要 JEDEC `t-1` 禁止/`t` 允许边界测试，以及 Ramulator2/DRAMsim3 的独立共同面对照。

## 4、DRAM 自刷新

### 4.1 先分清两种“刷新”

真实 DRAM 的存储单元会漏电，所以必须定期刷新才能保持数据。对控制器来说，有两种工作状态：

- **正常访问时**：控制器按间隔向 DRAM 发 `REFpb`、`REFdb` 或 `REFab`。这些是外部刷新命令，会占用相应 Bank/作用域，并让后续命令等待刷新时序。
- **自刷新时**：控制器先发 `SREFEN`，让器件进入 Self-Refresh 状态；这段时间不再从外部发送常规 REF。要恢复访问，控制器发 `SREFEX`，并等待退出恢复时间。

本项目模拟的是这两种状态对**命令、访问时间和功耗**的影响。

### 4.2 正常访问时，外部 REF

`RefreshManager` 记录“下一次该安排刷新的时间”。到达期限后，它记下一次待安排的刷新，并让 Controller 生成命令：HBM 的 per-bank 路径使用 `REFpb`，LPDDR6 的非 all-bank 路径使用成对 Bank 的 `REFdb`，all-bank 路径使用 `REFab`。对应代码是 [`src/controller/refresh.cpp:28`](src/controller/refresh.cpp:28)、[`src/controller/refresh.cpp:148`](src/controller/refresh.cpp:148) 和 [`src/controller/controller.cpp:1933`](src/controller/controller.cpp:1933)。

这里的 `credit` 可以简单理解为**待安排的外部刷新次数**：期限到了会增加，安排一个刷新批次会减少，见 [`src/controller/refresh.cpp:44`](src/controller/refresh.cpp:44) 和 [`src/controller/refresh.cpp:90`](src/controller/refresh.cpp:90)。

### 4.3 自刷新从进入到退出

1. **进入**：显式请求或自动低功耗策略触发 `SREFEN`。自动策略要等请求处理完、相关 Bank 关闭且空闲达到 `low_power_entry_cycles`；这个参数表示“空闲多久才进入”，**不是内部刷新周期**。见 [`src/controller/controller.cpp:655`](src/controller/controller.cpp:655)。
2. **驻留**：`SREFEN` 发出后，Controller/PHY 进入低功耗状态，普通读写不能直接执行。外部刷新期限仍向前推进，但这段时间**不新增待补发的外部 REF**；因为模型假定器件在自刷新状态下自行维持数据。进入前若已有 `credit`，代码并不会因进入 SREF 将其清零。见 [`src/controller/controller.cpp:1657`](src/controller/controller.cpp:1657) 和 [`src/controller/refresh.cpp:44`](src/controller/refresh.cpp:44)。
3. **退出**：有新工作或显式退出请求时发 `SREFEX`，再等待 `nSREFEX` 才恢复普通访问；驻留期间经过的那些外部刷新期限不会在退出后逐条补发。见 [`src/controller/controller.cpp:1665`](src/controller/controller.cpp:1665)。

例如外部刷新间隔为 100 tick，控制器在 tick 80 进入 SREF、tick 350 退出：100、200、300 这几个期限仍会使“下一次期限”向前移动，但不会因此积累 3 条退出后必须补发的 REF。这是**自刷新状态的模型假设**，不是代码真的向每一行存储单元发过 3 次内部命令。

### 4.4 自刷新功耗

模型逐 tick 累加真正处于 SREF 的时间，得到 `self_refresh_cycles` 和 `self_refresh_time_ns`；启用功耗模型时，按 **驻留时间 × 自刷新状态功率**计算 `self_refresh_energy_pJ`：

```text
自刷新能量(pJ)
  = VDD × IDD6x × idd_devices_per_rank × ranks
    × 驻留时间(ns) × power_scale
```

时间统计见 [`src/controller/controller.cpp:593`](src/controller/controller.cpp:593)，能量及背景热记账见 [`src/core/data.cpp:1404`](src/core/data.cpp:1404)，结果输出见 [`src/stats/result.cpp:293`](src/stats/result.cpp:293)。例如驻留 1000 tick，就按这 1000 tick 对应的时间计能量；**不会据此推断内部到底刷新了多少次**。入口次数也只是进入 SREF 的次数，不是内部刷新次数。

这与 DRAMsim3 按 SREF 驻留周期统计能量的思路相近；但本项目按 Controller/Channel 作用域建模，不能把 DRAMsim3 的 Rank 级状态直接等同过来。模型**没有**逐行内部刷新事件、漏电衰减或“漏刷后读出错误”的数据保持模型；因此可以分析低功耗驻留时间、访问阻塞和能量趋势，不能验证器件的保持时间。若 CLI 在最后一个请求完成后就结束，也不会额外计算后续待机时间；

**交付手册对应说明**：[2.4.5“Refresh、RFM/PRAC 与低功耗”](堆叠存储模型交付手册.md#245-refreshrfmprac-与低功耗)、[附录 A.5](堆叠存储模型交付手册.md#a5-refreshrfm低功耗和协议模式)、[8.1“当前模型完成度”](堆叠存储模型交付手册.md#81-当前模型完成度)。

## 5、Row hit 判断、统计

### 5.1 只看目标 Bank 当前打开的是哪一行

每个 Bank 同一时刻最多打开一行。假设请求要访问 **Row 7**，看这个 Bank 的 `open_row`：

| Bank 当前状态 | 这次请求算作 | 通常需要的行操作 |
| --- | --- | --- |
| 已打开 Row 7 | **row hit（命中）** | 不用为这次请求重新打开行；满足 Timing 后可进行读写 |
| 已打开 Row 5 | **row conflict（冲突）** | 先关闭 Row 5，再打开 Row 7 |
| 没有打开任何行（`open_row < 0`） | **row miss（未命中）** | 先打开 Row 7 |

因此，“miss”在这里特指**目标 Bank 当前没有打开行**；“conflict”才是**打开了别的行**。实际判断只比较目标 Bank 的 `open_row` 和请求的 Row，代码见 [`src/controller/controller.cpp:1765`](src/controller/controller.cpp:1765)。

### 5.2 为什么在发出第一条命令时判断

项目不是等到 RD/WR 才回头判断，而是在请求的**第一条命令真正发出、Bank 状态尚未被这条命令改变时**判断，调用位置见 [`src/controller/controller.cpp:1600`](src/controller/controller.cpp:1600) 和 [`src/controller/controller.cpp:1626`](src/controller/controller.cpp:1626)。

例如 Bank 原本关闭，请求先发 ACT 打开 Row 7、随后才发 RD。如果等 RD 时再看，Row 7 已打开，会把原本的 **miss 错记成 hit**。同理，冲突请求经过 PRE→ACT→RD，若在 RD 时判断也会被误算为 hit。所以这里的 `row_hits / row_misses / row_conflicts` 表示**请求开始接受服务时看到的行状态**，不是最终 RD/WR 发出时的行状态。

### 5.3 一次请求只记一次；统计命中不等于立刻可读写

一个请求可能经过 PRE、ACT、CAS、RD/WR 等多条命令，但只应提供**一个**行状态样本。首次分类后，`Request::row_status_counted` 被置为 true；后续命令不再重复分类，维护命令也不参加这项统计，见 [`src/controller/controller.cpp:1766`](src/controller/controller.cpp:1766) 和 [`include/hbm_sim/core/request.hpp:93`](include/hbm_sim/core/request.hpp:93)。

输出的命中率为：

```text
row_hit_pct = row_hits ÷ (row_hits + row_misses + row_conflicts) × 100%
```

计算见 [`src/stats/result.cpp:120`](src/stats/result.cpp:120)。分母是**首次调度时完成分类的普通请求数**，不是 RD 命令数，也不是所有已经完成的请求数。

最后要区分两个问题：统计上的 hit 表示“目标行已经打开”；一条 RD/WR **此刻能否发出**还要满足命令合法性和 Timing。在线状态检查在 [`src/controller/controller.cpp:2132`](src/controller/controller.cpp:2132) 形成 `row_hit` 条件，[`src/dram/state.cpp:35`](src/dram/state.cpp:35) 要求 Bank 已打开且行匹配；LPDDR 读写还要满足 WCK 条件。因此 **hit 不等于零等待**。

## 6、热模型坐标

### 6.1 三套坐标：地址、tile、thermal cell

一次命令有逻辑 DRAM 地址 `(Channel, PC, SID, Rank, BG, Bank, Row, Column)`；项目将地址映射到一个研究用 floorplan `(stack, layer, tile_x, tile_y)`，再把 tile 内部分成 `Gx×Gy` 个 thermal cell，得到 `(thermal_x, thermal_y)`。Dashboard 的 Layer 下拉框选的是 **layer**，鼠标提示的 `thermal(x,y)` 是**这一层热网格上的坐标**，不是原始 Bank 地址，也不是 `tile(x,y)`。一个热 cell 会汇总多次事件的能量与热状态；提示中的 DRAM 地址只是代表性位置，不等于该 cell 只有那个地址。映射入口见 [`src/core/data.cpp:815`](src/core/data.cpp:815)，展示逻辑见 [`tools/visualize.py:278`](tools/visualize.py:278)。

### 6.2 Bank 怎样放到 layer 和 floorplan tile

先把 BG/Bank 铺平成局部 Bank 编号：

```text
bank_index = bank_group × banks_per_group + bank
layers_per_sid = ceil(stack_height / sids)
layer = sid × layers_per_sid + bank_index % layers_per_sid
```

若超出 stack_height，代码会取模。这里的 layer 是**确定性地址映射到热层**，不是 JEDEC 给出的实际 die/Bank 版图；并非每个 layer 都覆盖全部 BG/Bank。代码见 [`src/core/data.cpp:831`](src/core/data.cpp:831)。

每个 `(Rank,SID,PC)` 组合在二维画布上分到一个纵向 slice。一个 slice 里用近似方形的网格摆放 `bank_groups × banks_per_group` 个 Bank 位置：

```text
banks_per_slice = bank_groups × banks_per_group
floorplan_cols = ceil(sqrt(banks_per_slice))
rows_per_slice = ceil(banks_per_slice / floorplan_cols)
slice = ((rank × sids + sid) × pseudo_channels) + pc
tile_x = bank_index % floorplan_cols
tile_y = slice × rows_per_slice + floor(bank_index / floorplan_cols)
```

`floorplan_cols` 只是实现选用的近方形排布规则，`slice` 只是为了让 PC/SID/Rank 坐标不相互覆盖；**不是器件版图依据**。见 [`src/core/data.cpp:852`](src/core/data.cpp:852)。

### 6.3 为什么示例显示 4 列 × 16 行

以当前 [`configs/hbm.cfg:152`](configs/hbm.cfg:152) 的 HBM3 8Hi 基准为例：`bank_groups=4`、`banks_per_group=4`，所以每个 slice 有 `4×4=16` 个 Bank 槽；`ceil(sqrt(16))=4` 列，`ceil(16/4)=4` 行。又有 `pseudo_channels=2`、`sids=2`（8Hi 的 auto 结果）、`ranks=1`，共有 `2×2×1=4` 个纵向 slice，于是 floorplan 画布是 **4 列 × (4 行/片 × 4 片) = 4×16**。配置 [`thermal_grid_cols_per_tile=1`、`thermal_grid_rows_per_tile=1`](configs/hbm.cfg:121)，所以每 tile 对应一个 thermal cell，热画布仍是 4×16；若改成每 tile 2×2，坐标画布会变为 8×32，而物理 DRAM Bank 数不变。

这里的“每层 4×16”更准确说是**每个 layer 共用的 4×16 坐标画布**，不是“每颗 die 被厂家切成 64 个物理格”。layer 按 SID 与 `bank_index % layers_per_sid` 选择后，某一层上只有部分位置被命令直接命中，其余位置可能为空，或因热耦合产生仅有温度的 cell。Dashboard 依据 thermal map 里的 `cols/rows/x/y` 重建网格，缺失点显示 `·`；不会强行制造 64 个有效 Bank 事件，见 [`tools/visualize.py:278`](tools/visualize.py:278)。

举例：若 PC=1、SID=0、Rank=0、BG=1、Bank=2，则 `bank_index=1×4+2=6`，`slice=1`，`tile=(2,5)`；8Hi 下 `layers_per_sid=4`，故 `layer=2`。当每 tile 为 1×1 时，其 `thermal=(2,5)`。这个例子同时说明：画布尺寸由**整个组织的可寻址 slice**决定，实际事件只落在计算出的某一 layer/cell。

### 6.4 tile 内细分、tooltip 与 -1 地址

若 tile 内热网格是 `Gx×Gy`，Row/Column 分别映到局部格：

```text
local_x = floor(row × Gx / rows)
local_y = floor(column × Gy / columns)
thermal_x = tile_x × Gx + local_x
thermal_y = tile_y × Gy + local_y
thermal_cols = floorplan_cols × Gx
thermal_rows = floorplan_rows × Gy
```

实现见 [`src/core/data.cpp:886`](src/core/data.cpp:886)。

热耦合还可能建立**没有命令直接命中**的邻居 cell。其 thermal 坐标和温度有效，但没有唯一 DRAM 地址，因此 tooltip 的 Channel/PC/SID/Rank/BG/Bank/Row/Column 记为 `-1`，表示 `coupling-only / address unknown`，不是“负地址”或模拟错误；见 [`src/core/data.cpp:1310`](src/core/data.cpp:1310)。颜色按当前层或全局温度范围缩放；相同颜色刻度模式下再比较冷热，见 [`tools/visualize.py:279`](tools/visualize.py:279)。

**交付手册对应说明**：[2.6.3“物理、功耗、热和 ECC”](堆叠存储模型交付手册.md#263-物理功耗热和-ecc)、[7.3.5“页面操作方法”](堆叠存储模型交付手册.md#735-页面操作方法)、[B.9.6“热结果和功耗的联合解读”](堆叠存储模型交付手册.md#b96-热结果和功耗的联合解读)。

## 7、LPDDR5/LPDDR6 命令的作用

### 7.1 RD、WR 与 CAS_RD、CAS_WR

`RD`、`WR` 是最终执行数据读写的命令：目标 Bank 必须已打开且 Row 匹配；RD 随后返回 payload，WR 进入 Direct 或 Behavioral PHY 的写数据路径。状态前提见 [`src/dram/state.cpp:39`](src/dram/state.cpp:39)，PHY 写入见 [`src/dram/mem_phy.cpp:247`](src/dram/mem_phy.cpp:247)。WR 后 Row 通常保持打开。

在项目支持的 split-CAS 序列中，`CAS_RD/CAS_WR` 是列访问的前置阶段，不是“又完成了一次读/写”：请求仍在 active buffer，直到后续 RD/WR 才 retire。见 [`src/controller/controller.cpp:1655`](src/controller/controller.cpp:1655) 与 [`src/controller/executor.cpp:225`](src/controller/executor.cpp:225)。

### 7.2 ACT1、ACT2 与 PREpb

LPDDR6 的 split activate 把激活地址分成 ACT1/ACT2：ACT1 开始并记录待配对状态，ACT2 按约束完成 Row 打开；单独的 ACT1 不代表已能 RD/WR。见 [`src/dram/state.cpp:50`](src/dram/state.cpp:50)、[`src/controller/executor.cpp:106`](src/controller/executor.cpp:106)。`PREpb` 关闭指定 Bank 当前打开的 Row，供 row conflict、行策略或刷新前清理使用，见 [`src/controller/executor.cpp:151`](src/controller/executor.cpp:151) 和 [`src/controller/controller.cpp:991`](src/controller/controller.cpp:991)。

### 7.3 REFpb、REFdb、REFab

`REFpb` 是单 Bank 刷新，`REFdb` 是 LPDDR6 的成对双 Bank 刷新，`REFab` 是目标 Rank/PC/SID 作用域全部 Bank 刷新。刷新前相关 Bank 要满足空闲/关闭约束，刷新后的 `nRFCpb/nRFC` 阻塞下一次激活；LPDDR6 配对及 Timing 见 [`src/controller/timing.cpp:86`](src/controller/timing.cpp:86) 与 [`src/dram/spec.cpp:339`](src/dram/spec.cpp:339)。原提问中的 `PEFpb` 应读作 `REFpb`；但在 LPDDR6 中不能把 `REFdb` 误称为单 Bank `REFpb`。公共枚举见 [`include/hbm_sim/core/common.hpp:53`](include/hbm_sim/core/common.hpp:53)。

### 7.4 不能把 LPDDR5 和 LPDDR6 合成一张命令表

两者共享读写、预充和刷新概念，但 LPDDR6 的 split activate、dual-bank refresh、WCK/CA 时序不能不加区分地套到 LPDDR5。项目由 `DramSpec` 的 `lpddr_family`、`split_activate`、`lpddr_dual_bank_refresh` 等能力选择执行路径；命令语义表见 [`src/dram/semantics.cpp:11`](src/dram/semantics.cpp:11)。

**交付手册对应说明**：[2.4.3“Bank 状态与命令语义”](堆叠存储模型交付手册.md#243-bank-状态与命令语义)、[第 4 章“四种标准模型”](堆叠存储模型交付手册.md#4-四种标准模型)、[C.3“LPDDR5”](堆叠存储模型交付手册.md#c3-lpddr5) 与 [C.4“LPDDR6”](堆叠存储模型交付手册.md#c4-lpddr6)。

## 9、可视化中 Injection-rate / latency / throughput 曲线

### 9.1 横轴：offered requests / tick

`performance_curve.py` 对每组 `standard × read_ratio_pct × inject_interval_ticks` 单独启动一次仿真，按 `offered_requests_per_tick = 1 / inject_interval_ticks` 生成横坐标，见 [`tools/performance_curve.py:57`](tools/performance_curve.py:57) 和 [`:76`](tools/performance_curve.py:76)。例如每 32、4、1 tick 提出一次请求，横坐标分别是 0.03125、0.25、1 **Host request/tick**。一个 tick 的实际物理时长由该点配置的 `tick_duration_ps` 决定；跨不同标准或速率比较时，1 request/tick 未必代表相同 requests/ns。

`offered` 指前端**尝试提供**的速率，不保证 Controller 每 tick 都接受这么多。队列满时可能停顿，实际完成速率还受排空尾段影响。这里的 request 也不是 ACT/RD/WR 命令；一般情况下一个 Host 请求可能拆成多个 DRAM transaction。当前 sweep 脚本还要求 `completed_reads + completed_writes == --requests` 才接受该点，见 [`tools/performance_curve.py:69`](tools/performance_curve.py:69)，所以它的默认扫点工作负载按这个 1:1 完成口径使用，不能不加检查地套到任意多事务 Host 请求。

### 9.2 左纵轴与实线：已完成 payload 吞吐量，单位 GB/s

每个彩色**实线**取 `achieved_bw_GBps`，来自仿真完成的 `read_bytes + write_bytes` 除以 `system_cycles × tick_duration_ps` 对应的秒数，再除以 `10^9`，见 [`src/core/system.cpp:1114`](src/core/system.cpp:1114) 和 [`tools/performance_curve.py:84`](tools/performance_curve.py:84)。这是有效读写 payload 带宽，不是接口上含 ECC/metadata 的比特率，也不是 `peak_bandwidth_GBps`。若想比较理论上限和效率，读取 JSON/CSV 同一点的 `peak_bandwidth_GBps`、`bandwidth_util_pct`；这两项**不是图中额外两条曲线**。

图例 `HBM3 R50`、`HBM3 R100` 中的 R50/R100 表示该组输入的 **50%/100% 读请求比例**，同色实/虚线属于同一组 sweep。颜色只是区分 `standard + read_ratio_pct`；不要把绿线理解为写带宽、蓝线理解为读带宽。绘图分组与左右轴见 [`tools/visualize.py:259`](tools/visualize.py:259) 至 [`:275`](tools/visualize.py:275)。

### 9.3 右纵轴与虚线：完成事务的平均延迟，单位 tick

彩色**虚线**使用右轴，不要按左边的 GB/s 读数。图上 `Latency series` 下拉框可在 `read transactions` 和 `write transactions` 之间切换，分别取该点的 `avg_read_latency_ticks` 或 `avg_write_latency_ticks`；`performance_curve.py` 从该次仿真的 `avg_read_latency`/`avg_write_latency` 读出，见 [`tools/performance_curve.py:80`](tools/performance_curve.py:80)。它们都是 Controller 接受事务到该事务完成的平均 **tick 数**，不是纯 `nCL/nCWL`，也不是 Host 端到端请求时间。换算纳秒为 `latency_ticks × tick_duration_ps / 1000`；若不同数据率/标准的 tick 时长不同，应换成 ns 才能比较真实时间。

当某个 sweep 点没有所选方向的完成事务（例如 R100 纯读时选 write latency），JSON 中为 `null`，该组虚线会缺失或只连接有样本的点，**不是 0 tick**。绘图的 `measured()`、左右两套比例尺、右上角最大值和下方 `with measured ... latency` 点数见 [`tools/visualize.py:263`](tools/visualize.py:263) 至 [`:275`](tools/visualize.py:275)。右轴最大值和左轴最大值是本次数据自动求得，不能比较两条线在画面上的“高度”来判断其数值谁更大。

### 9.4 每个点有哪些辅助指标、如何判断性能

图上的一个点对应**一次独立的确定性仿真**，JSON/CSV 还保存 `pattern`、`requests`、`system_cycles`、`completed_reads/writes`、读写延迟、`peak_bandwidth_GBps`、`bandwidth_util_pct`、`row_hit_pct`，生成位置见 [`tools/performance_curve.py:72`](tools/performance_curve.py:72)。曲线图本身只画 offered load、payload throughput 和所选方向延迟；Run summary/命令时间线来自单次 `--stats`/`--command-trace`，**未必就是曲线中的某一个点**。不能用 summary 中的 `achieved_bw_GBps` 去要求曲线某个点完全相等，除非该点的标准、请求数、负载、read ratio、配置和 seed 全部相同。

沿同色曲线从左到右看：低负载时吞吐随 offered load 上升、延迟接近基础访问时间；进入排队区后吞吐增幅收窄而虚线陡升；吞吐接近平台且延迟持续增长是饱和迹象。**平台值不是接口峰值**：仍要看 `bandwidth_util_pct`、行命中、刷新、写排空、反压与 Channel 分布。若吞吐反而下降，先核对每点完成性、`system_cycles`、请求分布及队列/刷新行为。脚本仅做趋势和 achieved≤peak 等自动 sanity check，见 [`tools/performance_curve.py:91`](tools/performance_curve.py:91)；这些检查不等于厂家性能校准。比较两次曲线还应固定组织、数据率、Stack/Channel、transaction bytes、pattern、seed、地址空间、Controller/PHY、refresh 等条件，否则无法归因。

**交付手册对应说明**：[7.3.3“生成性能曲线”](堆叠存储模型交付手册.md#733-可选生成性能曲线)、[7.3.5“页面操作方法”](堆叠存储模型交付手册.md#735-页面操作方法)、[8.6“性能曲线和不确定性”](堆叠存储模型交付手册.md#86-性能曲线和不确定性)。

## 10、`achieved_if_bw_GBps` 与 `achieved_bw_GBps` 

### 10.1 两个指标的计算口径与代码位置

两个指标使用相同的仿真时间分母，但分子不同：

```text
仿真秒数 = system_cycles / cycles_per_second
achieved_bw_GBps
  = (read_bytes + write_bytes) / 仿真秒数 / 1e9
achieved_if_bw_GBps
  = (interface_read_bytes + interface_write_bytes
     + ceil(interface_command_bits / 8)) / 仿真秒数 / 1e9
```

系统级公式见 [`src/core/system.cpp:1117`](src/core/system.cpp:1117)；单 Controller 的同类公式见 [`src/controller/controller.cpp:430`](src/controller/controller.cpp:430)。统计字段分别以 `achieved_bw_GBps`、`achieved_if_bw_GBps` 输出，见 [`src/stats/stats.cpp:210`](src/stats/stats.cpp:210)。`achieved_bw_GBps` 只计已完成读写事务的有效 payload；`achieved_if_bw_GBps` 另计配置指定的接口保护/元数据以及命令级 CA parity 开销。

每条读事务完成时，Controller 累计 `read_bytes` 和 `interface_read_bytes`，见 [`src/controller/controller.cpp:716`](src/controller/controller.cpp:716)；写事务对应位置见 [`src/controller/controller.cpp:740`](src/controller/controller.cpp:740)。单事务的接口字节数由 [`src/dram/interface.cpp:26`](src/dram/interface.cpp:26) 计算：先将 payload 字节换成 bit，加入协议附加 bit，再**按每条事务向上取整为 Byte**。命令级附加 bit 在命令发射时累计，见 [`src/controller/controller.cpp:1607`](src/controller/controller.cpp:1607)；系统计算带宽时再将其总和向上取整为 Byte。

### 10.2 cfg 中直接决定差额的参数

每事务附加位的求和代码见 [`src/dram/interface.cpp:9`](src/dram/interface.cpp:9) 和 [`src/dram/interface.cpp:17`](src/dram/interface.cpp:17)：

| 参数 | 对接口字节数的作用 |
| --- | --- |
| `metadata_bits_per_request` | 通用元数据位，直接加入每条事务 |
| `ecc_bits_per_request` | 通用接口 ECC 位，直接加入每条事务 |
| `hbm_link_crc_bits_per_request` | HBM 合成 CRC 位，直接加入每条事务 |
| `hbm_ras_metadata_bits_per_request` | HBM 合成 RAS 元数据位，直接加入每条事务 |
| `hbm_ecc_bits_per_request` | HBM 接口 ECC/元数据位，直接加入每条事务 |
| `lpddr_dbi_bits_per_request`、`lpddr_link_ecc_bits_per_request` | LPDDR 共用 metadata lane：取两者的**最大值**，不是相加 |
| `lpddr_ca_parity_enabled`、`lpddr_ca_parity_bits_per_command` | 前者启用时，按每条非 NOP LPDDR 命令累计后者指定位数；属于命令开销，不是每事务 payload 开销 |

这些参数可在 [`configs/hbm.cfg:103`](configs/hbm.cfg:103)、[`configs/hbm.cfg:173`](configs/hbm.cfg:173) 和 [`configs/lpddr.cfg:153`](configs/lpddr.cfg:153) 附近找到。最终判断要以该次运行的 `resolved.cfg` **生效值**为准，不只看模板中的默认值。

### 10.3 哪些 ECC 开关是间接相关、哪些无关

- `supports_ecc` 本身不直接进入带宽公式；在 HBM 配置解析中，它可能派生 `hbm_ecc_bits_per_request`，见 [`src/config/model.cpp:220`](src/config/model.cpp:220)。当前 HBM4 模板显式设置每个 32B 事务附加 16 bit，因此在没有其他开销时，接口记账为 34B/事务，接口需求带宽是 payload 带宽的 `34/32 = 1.0625` 倍。HBM3 默认 `supports_ecc = false`，相关附加位也为 0 时，两值相同。
- `lpddr_link_protection`、`lpddr_dbi_enabled` 等可能派生附加位；例如 LPDDR6 的 `link_protection` preset 明确设置 `lpddr_link_ecc_bits_per_request = 16`，见 [`configs/lpddr.cfg:216`](configs/lpddr.cfg:216)。**是否产生差额最终由生效的 bit 数决定**，不要只凭模式名称或布尔开关猜测。
- `[reliability.payload]` 中的 `ecc_shadow`、`ecc_check_on_read`、`ecc_correct_single_bit` 控制后端数据校验/纠错，不会仅因设为 `true` 就增加接口记账字节，见 [`configs/hbm.cfg:98`](configs/hbm.cfg:98)。同一个 HBM4 ECC 引脚上的位不应同时填进 `hbm_ecc_bits_per_request` 和 `hbm_ras_metadata_bits_per_request`，否则会在本公式中重复计数。

因此，当每事务附加位均为 0、没有命令级 CA parity 开销时，两指标相同；出现上述任一有效开销时，`achieved_if_bw_GBps` 通常更大。极小差额可能因终端显示精度而看起来相同。这里的接口带宽是**协议开销的等效需求记账**：这些 bit 当前不会自动延长数据总线占用周期，不能把它解释成引脚级实测吞吐量，见 [`include/hbm_sim/dram/interface.hpp:12`](include/hbm_sim/dram/interface.hpp:12)。

## 11、density 组只改 `rows`， `resolved.cfg` 的刷新 Timing 变化

这里的“只改 `rows`”指**实验显式覆盖的输入参数**，不是保证所有生效参数不变。对 HBM3 density 组，脚本分别设置 `rows = 8192 / 16384 / 32768`，其余组织维度保持基线，见 [`experiments/architecture_sweep/run.py:97`](experiments/architecture_sweep/run.py:97)。配置解析器据此重新计算地址几何容量，并由容量与 `stack_height` 推导每 die 的 `density_gb`，见 [`src/config/model.cpp:349`](src/config/model.cpp:349) 和 [`src/config/model.cpp:368`](src/config/model.cpp:368)。因此：

```text
显式 rows 改变 → 几何容量改变 → density_gb 改变
                 → 按密度/堆叠高度选择刷新时间 → nRFC、nRFCpb 改变
```

HBM3 当前 `resolved.cfg` 的实际值如下；三档数据率均为 6400 Mb/s/pin、堆叠高度均为 8Hi：

| case | rows | density_gb（每 die） | nRFC（nCK） | nRFCpb（nCK） |
| --- | ---: | ---: | ---: | ---: |
| `8gb_8h` | 8192 | 8 | 416 | 320 |
| `16gb_8h` | 16384 | 16 | 560 | 320 |
| `32gb_8h` | 32768 | 32 | 720 | 384 |

三份生效配置分别见 [`8gb_8h/resolved.cfg`](outputs/experiments/architecture_sweep/hbm3/density_8gb_8h/resolved.cfg)、[`16gb_8h/resolved.cfg`](outputs/experiments/architecture_sweep/hbm3/density_16gb_8h/resolved.cfg)、[`32gb_8h/resolved.cfg`](outputs/experiments/architecture_sweep/hbm3/density_32gb_8h/resolved.cfg)。HBM3 的刷新时间选值在 [`src/dram/profiles.cpp:47`](src/dram/profiles.cpp:47) 和 [`src/dram/profiles.cpp:75`](src/dram/profiles.cpp:75)，ns→nCK 换算在 [`src/dram/profiles.cpp:407`](src/dram/profiles.cpp:407)。因此 **`nRFCpb` 并非三档都不同**：8Gb 与 16Gb 都选到 200 ns，得到 320 nCK；32Gb 选到 240 ns，得到 384 nCK。按当前代码的来源标记，16Gb 的这两个值标为 JEDEC；8Gb 和 32Gb 使用研究型回退值，不能一概称为标准确认值，见 [`src/dram/profiles.cpp:442`](src/dram/profiles.cpp:442)。

若看的是 **HBM4** density 组，不能概括成“三档只改 `rows`”：`24gb_12h` 同时改变 `stack_height`、`sids`、`rows`，`32gb_16h` 改变 `stack_height`、`sids`，见 [`experiments/architecture_sweep/run.py:103`](experiments/architecture_sweep/run.py:103)。HBM4 的 `nRFC` 同时按每 die 密度和堆叠高度选值，`nRFCpb` 按密度选值；`nREFIpb` 也与堆叠高度有关，见 [`src/dram/profiles.cpp:283`](src/dram/profiles.cpp:283)。所以 HBM4 的 timing 联动来源不止 `rows`。

**这些变化不等于本次 density 负载实际执行了周期刷新。** 实验脚本只给 `refresh` 组设置 `supports_refresh = true`，density 组设为 `false`，见 [`experiments/architecture_sweep/run.py:309`](experiments/architecture_sweep/run.py:309)。`resolved.cfg` 仍记录完整生效 Timing，以便说明它构造的是哪一档模型；但不能仅凭 `nRFC` 不同，就把 density 组的性能差异归因于周期刷新。如果研究目标是严格“只改变行数、其余有效 Timing 完全固定”，应另做固定 Timing 的纯几何敏感性实验，并明确它不再是当前按密度联动刷新参数的配置。
