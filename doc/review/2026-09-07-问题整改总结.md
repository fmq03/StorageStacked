## 一、两条定案结论

### 结论一：协议基线是 v0.8 PDF，不是参考 RTL

之前有些字段布局是照着 Tenstorrent/BOS 的 AoU 参考 RTL 实现的。但 v0.8 的
changelog 明确写着：

> "Repurposed PROF/PROFEXTLEN fields as FLEX fields, defined use of FLEX
> fields as USER bits in the Basic Profile."

也就是说那份 RTL 早于 v0.8，其中的 PROF/PROFEXTLEN 布局在 v0.8 已经作废。
**凡 PDF 与 RTL 冲突处，一律以 PDF 为准。** RTL 仅作架构与 granule 参数的
旁证使用，不抄代码（它是 Apache-2.0，且自身标注 pre-release / evaluation
quality）。

### 结论二：带宽指标按口径B 考核，不再讨论

| 口径 | 定义 |
|---|---|
| 口径A | 应用字节 ÷（数据方向 Flit 数 × **256B**） |
| **口径B** | 应用字节 ÷（数据方向 Flit 数 × **240B**）← **合同考核口径** |
| 口径C | 应用字节 ÷（双向业务粒度 × 5B × 256/240），收发合算，最保守 |

理由三条：
1. v0.8 规范 Table 23 自己的效率表就是口径A，且明确写出 1024b 上限
   **88.9%** —— ≥90% 在口径A 下**物理不可达**。那 6B 链路开销 + 10B 协议头
   由 UCIe 和 AoU 规范固定，不由本单元决定。
2. 口径B 的分母 240B 恰好是本单元能支配的全部空间，衡量的正是"打包策略
   好不好"这件我们真正负责的事。
3. `口径A = 口径B × 0.9375`，换算关系是常数，信息不丢。报告里三个口径**全部
   打印**，甲方要看哪个都能立刻换算；但**只有口径B 参与门限判定**。

## 二、协议一致性类问题

| # | 问题 | 解决方案 | 验证 |
|---|---|---|---|
| 1 | CrdtGrant 线上格式带了不存在的前导 rsvd 和尾部 17bit | 按 PDF 字段表逐字段重排 | 黄金向量对拍 |
| 2 | USER 位按 RTL 的 PROF(4)+PROFEXTLEN(8)=12bit 实现 | 改为 v0.8 的 FLEX[15:0]，`AXI_USER_WIDTH` 12 → **16** | 黄金向量对拍 |

## 三、验证有效性类问题（最关键的一类）

### 问题：编解码器互为反函数，自洽 ≠ 正确

原来的验证是"MsgBuilder 编码 → MsgDecoder 能解回来 → 通过"。这是**无效验证**：
一个系统性的位域错误（比如整体位序反了）会让编码和解码同时错，但互相抵消，
整条链路全绿。上面第 1～3 条错误正是这样长期潜伏的。

### 解决方案：两道防线

**防线一：黄金字节向量对拍**（新增 `tb/tb_golden_vectors.cpp`）
从 v0.8 PDF 的字段表**手工转录**出每类消息的期望线上字节，与模型输出逐字节
比对。这条路径**完全绕开模型自身的编解码代码**，是唯一能抓住系统性位序错误
的手段。当前 3 种位宽各 **71 项检查全通过**。

**防线二：可辨识激励**
- 数据图样从"全 0xAA 这类均匀字节"改为**递增 ⊕ 走一位**。均匀字节会掩盖
  字节序错误 —— 每个字节都一样，顺序反了也看不出来。
- 地址从简单值改为 `0x0123456789abcdef` 这类每个 nibble 都不同的模式，
  并用独立解析器单独校验地址标签 / SIZE 等请求字段。

## 四、性能门限失守（本轮最严重的发现）

### 问题

门限选择代码写的是：

```cpp
#if AXI_DATA_WIDTH == 1024      // ← 恒为假
```

`AXI_DATA_WIDTH` 是 `axi_if.h` 里的 `constexpr int`，**不是宏**。C 标准规定
预处理器遇到不认识的标识符时替换成 0 再求值 —— 不报错、不告警。于是三种位宽
**全部落进 `#else` 分支，用的都是 256b 的门限**。

后果：1024b 的读带宽只要 ≥15.8 GB/s 就算通过，而 `effB_min` 被当成 0，
口径B 打印 `[SKIP] 不考核`。实测 42.66 GB/s 当然一路 PASS —— 但**门限根本
没有起到把关作用，口径B 这个合同指标实际处于失守状态**。

### 解决方案

改用 `-D` 传进来的真宏 `AXI_DATA_WIDTH_CFG`，并加 `static_assert` 兜底：

```cpp
#if   AXI_DATA_WIDTH_CFG == 1024
static constexpr PerfThresholds PERF_LIMITS{42.0, 41.5, 0.93, 12.0, 8.0};
...
static_assert(AXI_DATA_WIDTH_CFG == AXI_DATA_WIDTH,
              "AXI_DATA_WIDTH_CFG 与 AXI_DATA_WIDTH 不一致，性能门限会选错位宽");
```

以后任何人改了其中一个，**立刻编译失败**，而不是像之前那样悄悄退回 256b 门限。

### 验证（负向）

把 `effB_min` 临时抬到 0.99 重新编译，确认程序**以退出码 1 退出**并打印
`[FAIL] 口径B 链路载荷效率 94.79 % >= 99.00 %`，然后还原。门限确实会拦。

### 现行门限

| 位宽 | 读吞吐 | 写吞吐 | 口径B | TX 延迟 | RX 延迟 |
|---|---|---|---|---|---|
| 256b | ≥15.80 GB/s | ≥15.80 GB/s | 不考核 | ≤12ns | ≤8ns |
| 512b | ≥31.50 GB/s | ≥31.50 GB/s | 不考核 | ≤12ns | ≤8ns |
| **1024b** | **≥42.00** | **≥41.50** | **≥93%** | ≤12ns | ≤8ns |

256b/512b 不考核口径B，是因为这两档瓶颈在 AXI 侧（16 / 32 GB/s，低于链路的
48 GB/s），链路本来就填不满，考核链路载荷效率没有意义。只有 1024b 是
link-bound，口径B 才真正反映打包质量。

## 五、延迟模型类问题

| # | 问题 | 解决方案 |
|---|---|---|
| 5 | 文档写"往返值额外包含链路传输，每个 Flit 占 5.333ns" —— **这是错的** | 5.333ns 是 `FLIT_PERIOD_NS`，描述的是**速率**（满载时相邻 Flit 的最小发送间隔），不是飞行时间。空载时 LinkPacer 的预算是预填的，第一个 Flit 连这个间隔都不用付。默认单向飞行时间是 **0 ns**。文档已改正 |
| 6 | 链路飞行时间、对端处理时延写死 | 均改为可配置。新增 PERF-5：注入真实 40ns credit TAT |
| 7 | 速率与时延混在一个模型里 | 拆开：`LinkPacer` 只管速率；`FlitDelayLine<T>` 只管飞行时间，它是**一根线不是一个缓冲**，永不背压 —— 背压只来自 credit |

PERF-5 实测（三种位宽一致）：空载往返 10.00 ns → 注入 40ns TAT 后 50.00 ns，
增量 40.00 ns，**偏差 0.00 ns**，吞吐保持率 **100.00%**。

## 六、缓冲深度按错了口径（会直接掉吞吐）

### 问题

接收 FIFO 深度和初始 credit 原来是按链路 TAT（40ns）反推的。但 credit 从
"接收侧腾出空间"到"发送侧看见它"，中间还有三段被漏算了：

| 段 | 耗时 |
|---|---|
| ① 接收流水 | 2 拍 |
| ② credit 编码分档的余数等待（编码是 {0,1,4,8,16,32,64,128} 粗档，凑不满档要等下一轮） | 1~2 个 Flit 周期 |
| ③ 捎带在出站 header 上、或发一条专用 CrdtGrant | 1 个 Flit 周期 |

### 解决方案

```
CREDIT_LOOP_NS = LINK_TAT_NS + 3 × FLIT_PERIOD_NS = 40 + 3×5.333 ≈ 56 ns
在飞字节数 = 56 ns × 48 GB/s = 2688 B
深度 = ceil(2688B ÷ 每条消息的裸字节) + FIFO_MARGIN_ENTRIES(4)
```

| 位宽 | ReadData granule | 每条裸字节 | RDATA 深度 / 初始 credit |
|---|---|---|---|
| 256b | 8 | 42.7B | 68 / 544 |
| 512b | 14 | 74.7B | 41 / 574 |
| 1024b | 27 | 144B | 23 / 621 |

WriteResp 按周期算：`CREDIT_LOOP_CYCLES(28) + 4 = 32`（三种位宽相同）。

### 证据

按 40ns 算的深度，在真实 TAT 下吞吐掉到 **90.10%**；按 56ns 算，保持
**100.00%**。**这条结论要原样带进 RTL**，否则 RTL 会重犯同一个错误。

## 七、多 RP 下的同 ID 乱序风险

### 问题

AXI4 要求同 ID 同方向的响应保序。但 AoU 的多个 Resource Plane 是**相互独立
的流控平面** —— 各有 credit、各有 FIFO、发送侧 round-robin 轮询。两笔落在
不同 RP 上的事务，响应回来的先后顺序是**不确定的**。而本模型按
`AxQOS % RP_COUNT` 分流，如果 SoC 对同一个 AxID 发出了不同的 AxQOS，
同一个 ID 就被劈到了两个平面上。

### 解决方案：写成约束 + 运行时断言，**不做重排序缓冲**

**集成约束 C-1：同一个 AXI ID 在同一方向上未完成的事务，必须全部映射到
同一个 RP。**

充分条件（任一即可）：`RP_COUNT = 1`；或同一 AxID 只用一个 AxQOS；
或按 ID 空间静态划分（如 `AxID[9:8]` 直接当 RP 号）。

不做跨 RP 重排序缓冲的三条理由：
1. 面积随 outstanding 深度增长；
2. 会把快 RP 拖到慢 RP 的节奏上，**反而抵消了分平面的意义**；
3. AoU 规范本身没有要求桥接单元承担这件事。

实现：新增 `include/rp_order_guard.h`，读写各一张表（ARID=3 与 AWID=3 之间
没有顺序关系，不能共表）。写事务在 **B 握手**时销账，读事务要等 **RLAST**
才销账（否则一条 16 beat 的 burst 会被当成 16 笔重复释放）。违例计数经
`Axi2Flit::order_violations()` 暴露。

验证：TC9 两部分 —— 先确认已有 8 个合规用例**全程零误报**，再对检测器本身
做 5 项单元测试（含 ID 按 `AXI_ID_MASK` 截断后落到同一表项的边界情况）。

> **这条约束要由 SoC 的 ID/QoS 规划保证，桥接单元只能检出、不能修复。**

## 十一、给 RTL 阶段的三条提醒

1. **缓冲深度按 56ns 的 credit 环路算，不是按 40ns 的链路 TAT。** 按 40ns
   算，吞吐会掉到 90.10%。
2. **位序是 MSB-first**（v0.8 §5.8），且**必须用黄金向量对拍验证**。
   只靠"编码后能解回来"验不出系统性位序错误。
3. **三张数据消息的 granule 表不能互相代用。** 它们在 512b/1024b 下部分
   重合，只在 256b 下露馅。
