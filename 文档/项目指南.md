## 1. 平台与模型架构

这是“前端与系统平台 + 控制器 + 行为级 PHY + 存储语义及数据后端”的仿真器。
支持 HBM3/HBM4/LPDDR5/LPDDR6 的已实现命令与组织，不是模拟电压波形的电路仿真器。

```text
Frontend（合成流量 / trace / 外部请求源）
  ↕ HostRequest / HostResponse
MemorySystem
  ├─ Stack 0：入口队列 → 各 Channel Controller → 各 Channel MemPhy
  │                                               ↕ 协议适配 / 完成事件
  │                                      共享 MemoryImage → MemoryBackend
  └─ Stack N：同样的独立控制器、PHY、MemoryImage、Backend

Stats：旁路采集各层事件与去重聚合
Result：组织公共结果、格式化终端/JSON
Validators：独立重放命令/DFI，检查导出的行为
```

MemorySystem 是容纳、路由和推进各实例的系统层，不是在 MC 之外又串行增加一层存储。
Stats 不是 MC 到 PHY 的转发节点。MemoryImage 的 row buffer 保存 payload 和脏状态，
Controller 的 BankState 保存调度合法性；这两种状态各有职责。

### 1.1 主动与被动接口

- 主动系统：MemorySystem 接收 Host 请求，拆事务、选择 Stack/Channel、调度并返回响应。
  每个 [stack][channel] 有独立 Controller/PHY 状态；同 Stack 共享 MemoryImage。
- 被动模型：StackModel/MultiStackMemoryModel 接受外部控制器已经决定的命令，
  适合外部 UCIe/SystemC/RTL 适配器只需要 PHY + 存储模型时使用。
  外部适配器负责请求协议和 Stack 选择，不能把它当作又一套自动 MC。
- PHY：Direct 用于直通抽象，Behavioral 增加初始化、训练、流水线、队列和数据事件。
  两者都不是电气级引脚模型。DFI 输出是抽象事件/信号契约。

一个真实 HBM Stack 的独立接口，在本项目按 Channel 拆成多个 PHY 对象建模；
不能把“对象数”直接当作封装内物理 PHY 宏数量。多 Stack 不共享命令合法性和后端数据。

命令 FIFO 的条目按 command pipeline 到期释放。默认短流水线下，较深 FIFO 很难装满，
零命令反压只能说明当前负载没有填满队列，不能证明满足某种 CA 链路服务率。
当前没有独立的“每 M 拍释放 N 条命令”token-rate 参数，需该精度时应扩展服务模型。
显式 PDE/SREFEN 会让 PHY 进入 LowPower，须由 PDX/SREFEX 退出；外部驱动必须提供退出命令。
Controller 的空闲低功耗策略与这条显式 PHY 控制序列不是同一个接口。

### 1.2 协议差异与控制器组件

共同部分包括读写队列、调度器、行政策、地址映射、命令合法性、Timing 和维护请求。
协议特有部分保留显式实现：

| 模型 | 重点行为 |
|---|---|
| HBM | Channel/PC/SID 作用域、行列命令接口、same/different BG 与 SID Timing、刷新/RFM |
| LPDDR | 分拆 ACT、ACT 第二步的最早/最晚约束、WCK 窗口、bank-pair 刷新及模式切换 |
| PHY | 接收资格、流水线/队列占用、训练/低功耗、数据完成事件 |
| 存储层 | 字节掩码、初始化、行缓冲、转发与合并一致性、ECC、能量与热节点 |

相似的算法可以共享工具函数，但离线验证器不应直接等同于运行时裁决结果。
研究配置可以改组织与 Timing，但不能通过陌生策略名创造尚未实现的调度算法；
可选值和参数关系见 cfg 指南。

## 2. 构建与测试入口

需要 C++20 编译器、CMake（或 Make）、Python 3；Ninja 仅在选择 Ninja generator 时需要。
仿真核心不要求安装 Ramulator，外部差分时才需要它。

### 2.1 日常选一套构建

推荐 Clang + CMake，输出 build-clang-debug：

```bash
cmake -S . -B build-clang-debug -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build-clang-debug --parallel 4
./build-clang-debug/hbm_sim --help
```

G++ 可选路径，输出 build-gcc：

```bash
cmake -S . -B build-gcc -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++ \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build-gcc --parallel 4
```

这两套构建目录隔离，没有必要都执行。已有目录的编译器/generator 必须与缓存一致；
不要在同一个 CMake 构建目录切换编译器。VS Code 的 clangd 编译数据库应指向实际使用的目录。

也可用 Make，默认产物是 build/hbm_sim：

```bash
make CXX=g++ -j4
make test CXX=g++
```

Make 与 CMake 是构建入口的替代选择，不是先后依赖。Make test 使用 Make 的构建产物，
不会自动测试 build-clang-debug。对 CMake 产物使用：

```bash
ctest --test-dir build-clang-debug --output-on-failure
```

Debug 便于调试，Release 用于较大实验；两者应保持模型语义一致。
Sanitizer 是内存/未定义行为检查构建，不是更准确的 DRAM 模型；仅调试时按需运行
`make sanitize-test`，它会使用独立的 sanitizer 目录和编译/链接选项。
PHY 的测试程序与主程序共用库代码，不需要为 PHY 另建一套常驻工程。

`make test` 是聚合回归入口，包含下表前 14 项；执行它后不需要再把每个子目标重跑一遍。
单项入口用于定位某一模块的失败，不是废弃版本遗留。

| Make 目标 | 检查对象 | 是否包含在 test |

| scheduler-contract-test | 调度器选择及依赖契约 | 是 |
| result-test | C++ 类型化结果与 Python 输出/失败契约 | 是 |
| refactor-test | 共享辅助与运行接口回归 | 是 |
| phy-smoke | 经 CLI 的 PHY 集成路径 | 是 |
| visualization-smoke | 可视化输入和页面生成，不代替浏览器人工交互检查 | 是 |
| multistack-backend-smoke | 多实例数据后端及隔离 | 是 |
| multistack-demos-smoke | 自包含多实例 Demo 可运行性 | 是 |

| timing-boundary-validation | 命令 Timing 边界及报告生成 | 是 |

CMake/CTest 与 Make 提供相应检查，但扫描规模和测试包装不完全一样，
不要把两者通过次数相加当成独立验证证据。Sanitizer 运行的是仪器化后的检查，
不是另一份协议测试定义。失败先看首个失败目标和日志，不因最后汇总非零就判断所有模块失败。

外部参考只选一个目标，并传入真实源码路径：

```bash
make reference-validation RAMULATOR2_ROOT=../ramulator2
```

上例假设 ramulator2 与本项目目录并列；实际使用时换成参考源码的真实路径。
不要照抄 /path/to/ramulator2。参考模型支持的组织和 Timing 需要对齐，差分适用范围见审计。

完整架构实验示例：

```bash
python3 experiments/architecture_sweep/run.py \
  --binary ./build-clang-debug/hbm_sim --standards hbm4 \
  --requests 512 --out outputs/experiments/architecture_sweep_quick
```

它逐用例生成配置/运行产物，再聚合结果；字段解释统一见输出指南。
大规模扫描会耗时，先跑 smoke 或减少标准和请求数，再扩大矩阵。

## 3. 从运行到自定义

### 3.1 一次普通实验

```bash
mkdir -p outputs/quick
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --requests 128 --stats-json outputs/quick/result.json \
  --dump-resolved-config outputs/quick/resolved.cfg \
  | tee outputs/quick/summary.txt
```

终端默认是英文精简报告；机器分析读 result.json。
LPDDR 改用 configs/lpddr.cfg 并选择 lpddr5 或 lpddr6。
不要把 configs/validation/ 中单通道参考组织当作完整 Stack 的日常模板。
配置复制、逐项说明和修改后的联动检查只在 [cfg指南](cfg指南.md#usage) 维护。

### 3.2 合成流量与真实输入

stream 按步长生成地址；random 在有效地址域内按种子取样，读写比控制请求类型。
“合成”表示程序生成负载，不表示不经过控制器/PHY/后端。
真实应用 trace 则固定访问序列和可选到达时刻，适合重放同一工作负载。

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --pattern random --requests 512 --read-ratio 70 \
  --inject-interval 2 --seed 42 --random-address-space-bytes 1048576
./build-clang-debug/hbm_sim --config configs/lpddr.cfg --standard lpddr6 \
  --trace examples/sample.trace --requests 0
```

trace 基本语法：

```text
# 不写 cycle 时按 inject_interval 排程
R 0x1000
W 0x2000
100 R 0x3000
120 W 0x4000
```

写可携带 data=/mask=，读可携带 expect= 或 check=last_write。
BW/BR 是逻辑块访问，会按 Host 粒度展开；--requests 限制展开后请求数，不是原文件行数。
mask 必须与 payload 等长；非法负数、token 和越界地址直接报错。
完整 trace 格式与例子见 [examples](../examples/README.md)。

大负载可加 `--progress-interval 100000` 查看 stderr 进度；
终端结果只在结束汇总，所以暂时没有 summary 不代表死锁。
用 max_cycles 限制实验时必须检查是否 truncated，而不是把截断结果当作正常完成。

## 4. 带数据请求如何到达后端

以一条带 data 和 mask 的 Host burst 写为例：

1. Frontend 解析地址、长度、到达时刻、ID、payload 与 mask，保留未成功提交的请求。
2. MemorySystem 做地址/范围检查，按事务粒度拆分；子事务共享 Host 身份，
   用 transaction_index/count 区分，并切出各自字节与 mask。
3. 系统按地址选择 Stack，再以局部地址选择 Channel。入口队列满则反压，
   调用方重试原请求，不更换 ID、不提前记作已接收。
4. Controller 根据读写队列、依赖、行状态与 Timing 决定 ACT/列命令/PRE 等。
   BankState 维护命令合法性；数据不因“进入队列”就直接写到存储。
5. MemPhy 接收命令并产生协议适配、流水线及数据完成事件。
   Behavioral 的事件延迟不是电气信号传播求解。
6. 写请求完成时，MemoryImage 按 byte mask 提交数据并维护初始化、row buffer、
   version/ECC/功耗/热等语义，再由 MemoryBackend 保存 payload 与元数据。
7. Controller 产生 TransactionResponse；MemorySystem 收齐 Host 的子事务后给出
   HostResponse。写响应通常仅确认完成，不回传 data_hex。

读遵循相反的数据返回方向：获取对应字节和初始化标记，在完成点做期望值/ECC 检查，
再返回事务并按原偏移重组 Host 数据。读转发和写合并不能破坏同地址先后关系。
MemoryImage 的实际数据检查与 DFI 事件结构检查是两回事。

### 4.1 外部事件循环和完成状态

此接口是 C++ 请求/响应事务接口，类似 ready/valid 的接收契约，
**不是 AXI AW/W/B/AR/R 五通道逐拍引脚接口**；接 AXI/UCIe 需要适配器。

调用顺序示意（非独立可编译程序，system/source 由调用方建立）：

```cpp
// 配置响应模式后，始终保留提交失败的 pending 请求
while (source_has_work || !system.quiescent()) {
  if (pending && system.try_submit(*pending))
    pending.reset();
  system.step();
  while (system.has_transaction_response())
    consume_transaction(system.pop_transaction_response());
  while (system.has_response())
    consume_host(system.pop_response());
  // 按到达时间补充 pending，更新 source_has_work，并检查周期上限
}
system.finish(number_of_unsubmitted_requests);
```

维护命令走 try_submit_maintenance，不产生 HostResponse。
同一时刻在途 Host ID 必须唯一。注册观察 callback 不等于消费队列，仍需 pop。
批量流式 run 的 RunOptions 可选择 drain_responses，并提供两级响应回调；
CLI 导出响应使用统一驱动，按 always-ready host 消费，不能用它测真实 Host 长期拒收。

| API | 判断范围 | 用法 |
|---|---|---|
| idle() | 无在途执行/排队工作，不含对外响应队列 | 判断执行侧是否空闲 |
| responses_drained() | 对外保留响应是否全部消费 | 判断 Host/适配器是否仍欠收 |
| quiescent() | idle 且 responses_drained | 来源耗尽后安全退出的组合条件 |

选择 both 时必须消费两级队列；有界队列用于真实反压，不是“满了自动丢响应”。
请求源本身未耗尽时，仅 quiescent 为真也不能退出。外部调用 finish 汇总统计；
在周期上限退出时，传入尚未提交量，并记录此次截断。

## 5. 多 Stack 与存储后端

### 5.1 三种容量不要混用

- 逻辑几何容量：组织和事务粒度的乘积，公式见 cfg 指南。
- 后端地址上限：memory_capacity_bytes；不能靠它把 DRAM 逻辑组织扩大。
- 宿主分配量：稀疏 map/磁盘块/缓存实际使用，未必等于前两者。

多 Stack 地址先选实例，再转换为局部地址；每实例检查几何和后端边界。
缩小后端并不会自动缩小 random 的默认系统地址域。
因此使用小文件后端时，必须同时设置能够落在所有实例合法范围内的负载地址域。
stream 也应核对起始地址、请求长度和步长；有 trace 时检查 trace 中每个范围。

### 5.2 后端选择和持久文件

| backend | 宿主保存方式 | 适用点 |
|---|---|---|
| sparse | 内存稀疏行 | 小规模数据正确性和普通实验，不自动持久保存 |
| mmap_sparse | 稀疏文件映射 | 持久镜像、按需分配；映射不等于全部驻留 RAM |
| chunk_file | 文件 + 有界 chunk cache | 控制缓存驻留量，代价是换入换出与文件 I/O |

三者共用 MemoryImage 数据语义，不应改变同一请求序列的最终数据结果。
chunk cache 只约束相应缓存，不声称整个进程 RSS 被严格限定为 cache 大小。

持久后端的配套文件：

```text
data.bin          payload：每个逻辑 Byte 对应 1 Byte
data.bin.init     初始化位图：每个逻辑 Byte 对应 1 bit
data.bin.meta     固定头 + 每个后端 line 的元数据
data.bin.present  allocated 与 written 两个位图：各 1 bit/line
```

这是项目内部格式，不是 JEDEC 介质格式。稀疏文件的逻辑长度可以很大，
实际磁盘块按文件系统和触达范围分配；meta 大于 payload 并不自动说明损坏。
重开会核对格式版本、行大小和容量；正常 flush/析构保存计数信息。
它不提供断电事务一致性，异常终止的文件不能直接视为可靠 checkpoint。
开始独立实验使用新目录；重用已有文件表示恢复已有状态，不是清空后再跑。

### 5.3 一个可独立运行的多 Stack 后端查验

下例使用 2 个实例，每实例后端上限 1 MiB，并将随机聚合地址域限制到 1 MiB。
新建输出目录，避免改动已有镜像：

```bash
mkdir -p outputs
SIM_OUT=$(mktemp -d outputs/backend_check_XXXXXX)
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --stack-count 2 --requests 128 --pattern random --seed 42 \
  --random-address-space-bytes 1048576 \
  --memory-backend chunk_file --memory-capacity-bytes 1048576 \
  --memory-data-file "$SIM_OUT/data_{stack}.bin" \
  --memory-chunk-size 65536 --memory-chunk-cache-entries 4 \
  --dump-memory-image "$SIM_OUT/final_{stack}.txt" \
  --dump-memory-csv "$SIM_OUT/final_{stack}.csv" \
  --stats-json "$SIM_OUT/result.json" | tee "$SIM_OUT/summary.txt"
ls -lh "$SIM_OUT"
```

保留 {stack}，让不同实例输出到不同文件；mmap_sparse 改后端名并去掉 chunk 参数。
成功结束后再查看 final_*，字段说明见输出指南。运行已报错时，后续“找不到 final.csv”
是上游失败的结果，不能把 glob 字面量当作真实文件名。
比较不同后端需保持相同 seed/trace/组织，并用独立新目录保存，避免已有持久状态污染。

## 6. 功耗、热模型、坐标和 ECC

### 6.1 事件到能量

MemoryImage 记录读、写、激活、预充、维护与背景状态对应的模型能量。
配置型能量使用固定事件成本与每 Byte 成本，例如：

```text
E_read_pJ = (read_fixed_pJ + payload_bytes × read_pJ_per_byte) × power_scale
```

IDD 模式使用 VDD、相应电流及持续时间估计能量。例如读活动的动态差额可写为
VDD × max(IDD4R − IDD3N, 0) × burst_ns × devices（mA、ns 对应 pJ）。
ACT 项按 IDD0×tRC 减去相应 active/precharge 背景项估计，避免把动态与背景重复记账。
具体事件分支和系数使用 [data.cpp](../src/core/data.cpp) 的当前实现，
不能把研究配置的 IDD 数值称为已测器件电流。

### 6.2 地址如何映射到热位置

当前是可重放的研究映射，不是对厂家每一颗 die 的电路布局复原。以下是启用 floorplan 时的映射；关闭时 tile_x/tile_y 为 0，tile_z 仍取 layer。记：

```text
H = max(1, stack_height)
S = max(1, sids)
b = bank_group × banks_per_group + bank
L = max(1, ceil(H / S))
layer = (sid × L + b mod L) mod H
F = ceil(sqrt(bank_groups × banks_per_group))
R = ceil((bank_groups × banks_per_group) / F)
slice = (rank × S + sid) × pseudo_channels + pc
tile_x = b mod F
tile_y = slice × R + floor(b / F)
tile_z = layer
grid_x = min(grid_cols-1, floor(row × grid_cols / rows))
grid_y = min(grid_rows-1, floor(column × grid_rows / columns))
thermal_x = tile_x × grid_cols + grid_x
thermal_y = tile_y × grid_rows + grid_y
thermal_z = layer
```

grid_cols/grid_rows 对应每 tile 热网格设置；subarray/mat/cell/microbump 是进一步的研究坐标，
其确定性映射也在 MemoryImage::physical_address 中，不应由截图倒推厂家版图。
HBM height 建立多层索引；LPDDR 高度为 0 时使用一层映射，不解释成没有存储。
主模板的 HBM `sids=auto` 在几何解析阶段随 4/8/12/16Hi 选择 1/2/3/4；
显式 SID 不随层数改写。这里的 layer 映射使用最终解析值，不再单独推导 SID。

当前热节点 key 是 (stack, layer, thermal_x, thermal_y)，**没有单独的 channel 维度**。
因此不同 Channel 的地址可能汇入同一热节点，不能宣称每 Channel 在图中完全物理隔离。
修改 bank/行列/热网格会改变节点映射和事件分布；跨实验比较需要保存组织参数。
耦合邻居使用自身的 thermal 坐标反算 tile/grid，不继承源节点的 tile 位置。
一个热节点不能唯一反解成 DRAM 地址：直接事件记录代表地址，仅耦合节点的未知地址字段
用 -1 表示；导出标识见[输出指南](输出指南.md#74-热图和可视化阅读)。

### 6.3 温度更新与空白区域

事件先更新对应节点能量，再按每 tick 的经验冷却和温升系数更新：

```text
cool = min(1, delta_tick × thermal_cooling_per_cycle)
T = T − (T − ambient) × cool
T = T + E_pJ × thermal_rise_c_per_pJ
```

启用稀疏耦合时，与横向/纵向邻居按温差及受限耦合系数转移温度增量；
TSV 面积/热导设置可影响纵向耦合。实现是事件驱动、顺序更新的简化模型，
不是按材料完整求解热容、边界条件和三维偏微分方程。

节点按事件或耦合惰性创建，导出只覆盖已有节点。图上空白是“未导出节点”，
不是零温度或确认的环境温度。平均值受已创建节点集合影响；短时间实验不能代表稳态热设计。
节点首次收到直接命令时保留先前耦合产生的温度，再按时间冷却和叠加新事件；
`events=0` 仅表示尚无直接事件，不意味着该节点没有温度状态。
HBM 使用 Stack/layer/TSV 研究拓扑；LPDDR 使用简化器件映射，均需厂商几何与热参数校准。
热图颜色及统计口径见输出指南，不在这里重复字段表。

### 6.4 ECC、初始化和链路保护

未写字节有独立 initialized mask，不能仅以 payload 恰好为零认定有效。
payload ECC shadow 维护软件校验信息，可配合数据注错观察纠正/不可纠正行为；
checksum、ECC 和独立读 expect 各自证明不同性质。
链路保护/效率是接口侧传输与开销模型，不等同于 payload ECC，
更不是完整厂商 on-die ECC、训练波形或故障安全证明。验证边界见审计。

## 7. 导出和可视化操作

### 7.1 生成一套产物

```bash
mkdir -p outputs/artifacts
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --requests 128 --response-delivery-mode both \
  --host-response-queue-capacity 16 --transaction-response-queue-capacity 64 \
  --response-trace outputs/artifacts/host_responses.csv \
  --transaction-response-trace outputs/artifacts/transaction_responses.csv \
  --cmd-trace outputs/artifacts/commands.csv \
  --dump-timing-table outputs/artifacts/timing.csv \
  --stats-json outputs/artifacts/result.json \
  | tee outputs/artifacts/summary.txt
python3 tools/visualize.py \
  --command-trace outputs/artifacts/commands.csv \
  --stats outputs/artifacts/result.json --out outputs/artifacts/dashboard.html
```

打开生成的 HTML 即可浏览，不需要外部网站服务。额外 DFI、热图和性能曲线需要在运行
和可视化两端分别启用对应导出/输入选项，具体键见 cfg 指南。
多 Stack 的 thermal-map 可重复传入多个真实文件；先检查文件存在并保留 stack 标识。

`make visualize-example` 可以直接生成 outputs/visualization/example/dashboard.html；
它使用 Make 的二进制。与上述命令二选一即可，不要求先跑两套程序。

### 7.2 调试页面

先确认 commands 非空、result JSON 有效、各路径属于同一次运行；
再在浏览器开发者工具 Console 查看脚本错误。过滤条件与 lane 上限会隐藏部分数据，
先 Full range、取消筛选，再定位指定 stack/channel/request。
页面没有性能曲线可能只是未提供 performance JSON；没有热图也可能未启用热模型/导出。
读图含义和诊断表详见输出指南，命令时序的最终判定使用独立验证器，不依赖截图。

- 新后端：保留 byte mask、初始化、元数据及重开检查契约，与 sparse 做数据差分。
- 校准：替换有证据的参数并保留来源和适用模式，执行相关 Timing/数据/参考验证，按审计界定声明。
