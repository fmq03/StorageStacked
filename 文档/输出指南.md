# 输出指南

本文负责普通输出、公共 JSON、专项 diagnostic 字段和性能分析。配置含义见
[cfg指南](cfg指南.md)，架构、热计算与文件后端原理见[项目指南](项目指南.md)，
可信度门槛见[审计](审计.md)。同一字段只在下文一个位置定义；诊断中出现的同名公共字段沿用该定义。

<a id="summary"></a>

## 1. 模型、参数、结果三部分

默认使用 `summary` 模式，输出模型、参数和结果的精简报告；
也可通过 `--stats-view summary` 显式选择。
终端统一使用英文标题 `MODEL / PARAMETERS / RESULTS` 和英文指标标签，
用户自定义名称原样保留；中文只用于文档说明。JSON 使用独立的机器字段和单位。

内容仍分为三部分：

- 模型：类型、Channel/PC/SID 或 Subchannel/Rank 组织、Bank/行列、计算容量、请求粒度和工作规则。
- 参数：接口速率、时钟、负载、队列容量，以及相对程序内置基准的参数变化摘要。
- 结果：完成性、时间、吞吐量、读事务延迟、行命中率、检查结果；能量和温度按启用状态附加。

HBM 的中性 Rank=1 不单列；非 1 的实验 Rank 会显式提示，不能隐去影响容量的维度。
LPDDR 使用器件/Subchannel/Rank 标签。组织打印的是逻辑寻址层级，不把 SID 等同于一颗物理 die。
单控制器验证模式额外警告：配置组织容量不表示实际模拟了全部 Channel。

容量显示几何推导的 GiB，不代表后端实际分配量；公式及 density/stack 关系见
[cfg指南的联动说明](cfg指南.md#coupling)。后端分配字节是数据行记账，不是 RSS 或磁盘占用。

典型使用：

```bash
mkdir -p outputs/result_example
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --requests 128 --stats-json outputs/result_example/result.json \
  --dump-resolved-config outputs/result_example/resolved.cfg \
  | tee outputs/result_example/summary.txt

python3 tools/view_stats.py outputs/result_example/result.json \
  --keys standard,host_requests,dram_transactions,simulation_time_ns,achieved_bw_GBps,avg_read_latency_ns
```

summary.txt 用于人读，不是机器键值接口。可视化的 `--stats` 和工具输入应使用 result.json。
不要用 `rg '^system_cycles' summary.txt` 判断指标丢失。
交付手册中的普通运行同样遵守这一约定：同名 `stats.txt`/`stats.json` 分别供人读和工具读取，
普通运行无需开启诊断模式。专项诊断单独见
[交付手册 7.1.2](../堆叠存储模型交付手册.md#section-7-1-2)，其完整输出保存到独立文件，
不混入普通性能结果；字段缺省不等于零。命令行 `--stats-view diagnostic` 会覆盖
配置里的 `stats_view=summary`；该模式仅用于专项诊断。
机器结果按语义分区，metrics 只保存公共运行指标；完整复现参数保存在 resolved.cfg，
命令/DFI/数据/热图仍由相应的导出选项产生，结果 JSON 不会自动启用这些轨迹。


### 1.1 终端英文标签逐项说明

终端是人读报告，英文标签不等于 JSON key。单位和语义如下：

| 终端标签 | 含义/查看要点 |
|---|---|
| Model / Standard | 自定义模型名与实际基础协议 |
| Organization | 实例 × channel × PC/SID 或 SC/rank 的逻辑组织 |
| Experimental Ranks / Experimental SIDs | 仅非中性实验维度出现；不能从容量解释中漏掉 |
| Bank / Row / Column | 每逻辑范围的 BG/bank 和每 bank 的 row/事务列 |
| Capacity | 每实例及聚合几何容量，GiB |
| Host / Transaction Bytes | Host 粒度 / 单 DRAM 事务 payload 字节 |
| Policies | 调度、行政策、地址映射、channel 和 Stack 路由策略的生效值 |
| Features | PHY、后端、refresh/RFM、payload ECC 是否启用；不是验证状态 |
| Interface / Clock | 每 pin 数据率、每实例位宽、CK 与 tick 时长；LPDDR 附 WCK:CK |
| Workload | synthetic/trace、请求规模、读比例、注入间隔 |
| Address Space / Seed | 合成地址域和种子；stream 还显示步长 |
| Read / Write Queues | 每控制器读/写队列配置容量 |
| Comparison Baseline | 当前程序内置基准名和有效参数差异总数，详见第 2 节 |
| Parameter Change | 最多两项额外变化摘要，完整列表在 JSON changes |
| Run Status | completed/truncated/failed；不能只看进程输出了数字 |
| Requests / Transactions | Host 数、已完成读写事务和提交事务数 |
| Remaining Work | 未注入/排队工作与 pending 完成项分开显示，不是纯 Host 数 |
| Simulation Time | 模型时间，ns；不是宿主程序执行耗时 |
| Bandwidth / Utilization | 有效 payload GB/s / 占理论峰值百分比 |
| Read Transaction Latency | 读事务平均延迟，ns；无读时 N/A，不是 Host burst 完成延迟 |
| Row Hit Rate | 首次调度分类的行命中百分比，不是后端 rowbuf 命中 |
| Validation | Command/DFI 是否实际检查、独立读检查量及数据错误量 |
| Energy | 可选累计模型能量，pJ；不是功率 |
| Mean / Peak Temperature | 可选触达节点空间平均/历史峰值，摄氏度 |
| Backend Allocation | 后端分配行数和数据字节记账 |
| Golden Check | 启用 golden 时的比较记录数和错误量 |
| Stack 结果表 | 每实例完成读写、吞吐和读事务延迟；不累加延迟求系统延迟 |
| WARNING | 非中性组织、数据/ECC 或模型对象不一致等需要核查的条件，不应忽略 |

<a id="changes"></a>

## 2. 参数变化比较的基准

比较对象是**当前程序内置的同标准模型（按配置 schema 3 解析）及 CLI 默认选项**，
不是修改后的配置文件自己，也不是 JEDEC 或厂商认证型号。终端和 JSON 都记录该基准名称。

比较实际生效的 resolved 参数，因此直接修改 [standard.*.organization] 或 Timing 段也能发现。
基本负载、请求数和已显示的参数无需重复罗列；不因 [override] 是否出现而决定有没有变化。
同一 Timing 数值从 jedec 标签改成 vendor 不算数值变化，来源仍由 resolved.cfg / Timing 表审计。

终端最多列两条尚未在结构摘要中体现的变化（优先 Timing），并明确总数；JSON 的 changes 保存完整比较清单。
变化值包含自动推导的结果，不声称每项都是用户直接输入。例如改 columns，
容量和几何折算 density 会同时变化。内置基准和主模板存在有意的队列/PHY 默认差异，
因此未改模板也可能有变化记录，这不代表配置错误。

比较清单不替代配置来源审计。`--dump-config-diff` / `--compare-preset`
采用配置层对比口径，不等同于结果中的内置基准比较。
运行复现应保存完整配置、resolved 快照及源码/二进制版本；改变程序版本可能改变内置基准。

<a id="json"></a>

## 3. JSON schema 2

配置 schema 与结果 schema 是两个独立版本。结果由 C++ 类型化值直接序列化，
精度独立于终端展示时的四舍五入。

| 分区 | 内容 |
| --- | --- |
| schema_version / run_status / error | 格式版本，以及 completed / truncated / failed 和错误信息 |
| model | 实际模型身份、组织、规则、启用状态，不算性能指标 |
| parameters | 本次接口和负载的关键参数 |
| metrics | 下面列出的精简运行指标，不重复配置 |
| validation | 命令/DFI 状态及检查量、数据检查/错误量、ECC 不可纠正错误量；执行 Golden 验证时附加检查量 |
| comparison_baseline / changes | 比较基准及完整有效值变化列表 |
| stacks | 每实例完成读写数、带宽、平均读事务延迟，用统一列结构表达 |
| diagnostics | 仅显式 diagnostic 模式附加，不是公共指标契约 |

metrics 的固定候选集合如下；未启用的功耗/热字段不生成：

| 字段 | 单位与含义 |
| --- | --- |
| host_requests | 成功接收的 Host 请求数，不是完成的 Host 响应数 |
| dram_transactions | 拆分后的提交事务数 |
| completed_reads / completed_writes | 完成的 DRAM 事务数，包含相应的转发/合并完成路径 |
| remaining_requests | 排队/未注入的混合工作量，可能含维护请求，不能解释成纯 Host 数 |
| remaining_pending | Controller pending 完成项；与 remaining_requests 分开 |
| hit_cycle_limit | 因周期上限而未完成 |
| system_cycles / simulation_time_ns | 系统 tick 数 / 物理仿真时间，不累加 Controller 周期 |
| read_bytes / write_bytes | 完成事务的 payload 字节数 |
| achieved_bw_GBps | 十进制 GB/s，有效 payload 吞吐量 |
| peak_bandwidth_GBps / bandwidth_util_pct | 理论峰值 / payload 吞吐占峰值百分比 |
| avg_read_latency_ns | 平均读事务延迟，非 Host burst 重组延迟；没有完成读时为 null |
| row_hit_pct | hits / (hits + misses + conflicts) × 100；无分类请求时为 null |
| storage_lines_allocated / storage_bytes_allocated | 后端分配行数 / 该层的数据字节记账 |
| power_energy_pJ | 启用功耗模型时的累计能量 |
| thermal_avg_temp_C / thermal_peak_temp_C | 启用热模型时的平均/峰值温度 |

行访问在请求首次参与调度时分类一次；它不是后端 rowbuf_hits 的命中率，
分母也不必等于 Host 请求数或所有完成事务数。

物理时间换算：tick_duration_ps = tCK_ps / tick_multiplier；
simulation_time_ns = system_cycles × tick_duration_ps / 1000；
平均读事务延迟同样从其 controller tick 口径换算。
这是模型时间，不是仿真程序的墙钟耗时。DVFS 使用当前模拟器的时间记账口径，
该结果不是逐段变频时钟积分。

### 3.1 非 metrics 分区如何读

model 中的组织、策略和能力键，以及 parameters 中的速率、时钟、请求源和队列键，
沿用 [cfg指南](cfg指南.md#reference) 中同名配置的单位，但这里记录的是生效值，不是原始文本。
下列结果专用项应区别处理：

| 分区/字段 | 解释 |
|---|---|
| model.model_name / standard / model_conformance | 可读身份、基础协议及本次模型符合性分类，不是厂商认证 |
| model.capacity_per_instance_bytes / aggregate_capacity_bytes | 几何计算的每实例 / 聚合 Byte 容量 |
| parameters.input_kind | synthetic 或 trace；trace 结果省略不适用的合成参数 |
| parameters.effective_random_address_space_bytes | 本次实际采用的随机地址范围；与原配置 0=自动分开 |
| parameters.tick_duration_ps | 每个执行 tick 的时长，ps |
| validation.cmd_validation / dfi_validation | 实际检查状态；JSON 用 not_run 表示未执行 |
| validation 中检查量/错误量 | data_checked_reads、data_mismatches、cmd_validation_checked、dfi_validation_events、ecc_uncorrectable_errors，以及启用的 golden 字段；分别见 6.4–6.8 的精确含义 |
| stacks[].stack | 实例编号；每行的 completed_reads/writes、achieved_bw_GBps、avg_read_latency_ns 采用与系统同名指标相同的单位 |
| changes | 相对 comparison_baseline 的有效参数变化列表，语义见第 2 节 |

HBM 的中性 ranks、LPDDR 的中性 sids 等按协议隐藏；未出现不代表零维组织。
机器使用者应读结构化 JSON，不从终端的一行复合标签拆字符串。

<a id="validity"></a>

## 4. 检查状态与失败结果

- 命令/DFI 检查未启用是 not_run，不是 pass。
- data_checked_reads=0、data_mismatches=0 不构成独立数据正确性证据。
- DFI 结构自洽不等于请求提供独立 expect 的数据验证。
- 没有读事务时延迟 null；未启用功耗/热模型时字段缺省，不能当成零测量。
- ECC 不可纠正错误和容量不一致不会因为精简而被静默隐藏。
- truncated/failed 不允许无标记进入有效性能曲线。

已确定结果路径后、执行开始前，指定 JSON 先写为未完成的失败状态；
成功结束后替换。后续输出异常会把最终状态设为 failed，不保留成功状态副本。
参数解析失败可能尚未确定路径，所以**首先检查进程退出码**，不要只读取旧文件。

实验工具还要求：未达周期上限、remaining 两项为零、无数据不匹配、
完成读写之和等于 dram_transactions、所需字段存在且类型和数值有效。
这些条件不证明厂家准确性；性能比较仍需相同 trace/seed、地址域、后端、
调度策略及实际时序。固定 requests/tick 与固定 requests/ns 不是同一负载口径。

<a id="diagnostic"></a>

## 5. 专项诊断与工具读取

需要检查 PHY FIFO、维护、数据后端、响应导出或 Timing 来源时，显式请求：

```bash
mkdir -p outputs/result_audit
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --requests 128 --stats-view diagnostic \
  --stats-json outputs/result_audit/result.json \
  > outputs/result_audit/diagnostic.txt

rg '^(phy_command_backpressure|data_checked_reads|host_responses_exported)\s*:' \
  outputs/result_audit/diagnostic.txt
```

diagnostic 保留专项验证确实使用的内部计数和配置键；它不是另一份默认公共指标。
其键排序输出，不能依赖固定行号。JSON 中 diagnostics 也是显式选择才附加。
内部事件计数仍可用于 C++ 测试，不为了输出变短而破坏模型运行或验证。

需要 bytes/tick 时，用 payload 字节数除以 system_cycles。队列平均占用在诊断中
使用 *_q_avg_per_ctrl，分母为 aggregate_ctrl_cycles。
Host/transaction、控制器/后端行命中、payload/interface 带宽具有不同语义，不能互相替代。
接口速率专项校验使用 if_xfer_rate_Gbps。

程序应按 model/parameters/metrics/validation 分区读取 JSON，或调用 tools/result_io.py。
项目读取器接受诊断键值文本、JSON schema 1 和 schema 2，提供供分析工具使用的平面视图。
其中 avg_read_latency 按 ns 换算回 tick；公共 JSON 的 avg_read_latency_ns 在无读请求时为 null。
读取器的 tick 延迟辅助字段在无读时为 0，使用时必须同时判断 completed_reads。
缺失必需指标会报错；人读摘要不能用作机器结果。整数计数不经浮点转换。

普通可视化、性能曲线和敏感性分析读取公共结果，不要求诊断字段。
性能曲线文件的 avg_read_latency_ticks 明确使用 tick 单位，row_hit_pct 使用百分比；
曲线格式与模拟器结果格式是独立接口。敏感性实验仅在启用功耗/热模型时输出能量和温度，
字段缺省不能解释成零测量。

## 6. 全输出字段字典

本节只定义诊断新增字段。第 3 节公共字段在 diagnostic 中仍同义，不重复列出。
配置快照与 [cfg指南](cfg指南.md#reference) 同义；以下仅解释特殊改名和统计口径。
“字段族”中的 N 或 * 是占位符，不是可直接检索的字面键。

<a id="appendix-b-1"></a>

### 6.1 身份、周期和完成

| 字段 | 解释 |
|---|---|
| `standard` | 当前标准 |
| `timing_profile`、`vendor_profile` | profile 与 vendor 标签 |
| `timing_source_*` | timing 字段来源 |
| `cycles` | 兼容周期字段；当前系统聚合报告与 system_cycles 同口径，仍推荐使用后者 |
| `aggregate_ctrl_cycles` | 所有 controller 周期求和 |
| `injected_requests` | 成功注入系统的 transaction 数 |
| `reads`、`writes` | 读写 transaction 数 |

<a id="appendix-b-2"></a>

### 6.2 性能、延迟和队列

| 字段 | 解释 |
|---|---|
| `avg_read_latency` | 完成读 transaction 的平均 controller tick 延迟 |
| `read_q_avg_per_ctrl`、`write_q_avg_per_ctrl`、`priority_q_avg_per_ctrl`、`active_q_avg_per_ctrl` | 队列占用累计值除以 aggregate_ctrl_cycles |
| `injection_stall_cycles` | frontend 因系统拒收而停顿的周期 |
| `achieved_if_bw_GBps` | 包含 metadata/ECC 的记账等效接口需求带宽；不是 pin-accurate 实测值 |
| `interface_read_bytes`、`interface_write_bytes` | payload 加接口开销后的读写等效需求字节 |
| `interface_overhead_bits`、`interface_command_bits` | 数据保护/metadata 总开销和命令保护记账 bit；细分项见 6.8.7 |
| 按需派生的 bytes/tick | 使用 read_bytes/write_bytes 除以 system_cycles |

这里的“接口字节”是配置开销的等效需求记账，不是完整 DQ 物理槽计数。
例如 LPDDR6 BL24 × 12 DQ = 288 bit，其中 256 bit 为 32 B payload，
其余 32 bit 为非数据槽。关闭保护开销记账时，`interface_*_bytes` 仍可等于 payload，
不代表物理上只传了 256 bit；也不能无条件给所有模式再加 4 B，以免与已配置 metadata 重复。
DBI 与 Link ECC 的共享 lane 当前按最大位宽而非两者求和。HBM ECC pin 的接口开销
与存储后端 ECC shadow 是两套概念，后者不自动增加接口字节。

<a id="appendix-b-3"></a>

### 6.3 行行为和命令

| 字段/字段族 | 解释 |
|---|---|
| `row_hits`、`row_misses`、`row_conflicts` | 调度时行缓冲关系 |
| `commands.ACT/ACT1/ACT2` | 激活/分裂激活数 |
| `commands.PRE/PREpb/PREab` | 预充数 |
| `commands.RD/WR/RDA/WRA` | 列读写及自动预充命令数 |
| `commands.CAS_RD/CAS_WR` | LPDDR CAS 同步/列入口计数 |
| `commands.REFab/REFpb/REFdb` | 各刷新命令数 |
| `commands.RFMab/RFMpb` | RFM 命令数 |
| `commands.MRW/MRR` | 模式寄存器命令数 |
| `commands.WCK_SYNC/WCK_TRAIN/DVFS` | LPDDR WCK/DVFS 命令数 |
| `commands.PDE/PDX/SREFEN/SREFEX` | 低功耗命令数 |
| `commands.ECC_SCRUB/RAS_ERR` | RAS 行为命令数 |
| `maintenance_requests`、`maintenance_served` | 请求和已服务维护事务 |
| `refresh_batches`、`refresh_pb_batches`、`refresh_ab_batches` | 刷新批次及 per-bank/all-bank 批次 |
| `refresh_postpones`、`refresh_pullins`、`refresh_credit_peak` | 刷新调度行为 |
| `rfm_events`、`rfm_pb_events`、`rfm_ab_events` | RFM 总事件数及 per-bank/all-bank 事件数 |
| `dual_issue_cycles` | HBM 行列双总线同拍发射周期 |
| `row_bus_issues`、`column_bus_issues`、`unified_bus_issues` | 总线发射计数 |
| `rising_edge_ticks`、`falling_edge_ticks` | 启用 HBM edge pairing 时，所有 controller 观察到的上升/下降相位 tick 聚合计数；无论该 tick 是否发令都会增长，不能当成 CA 利用率 |
| `write_mode_cycles` | 所有 controller 处于写 drain 模式的周期聚合值 |

<a id="appendix-b-4"></a>

### 6.4 数据、后端与拓扑

本节列出的均为当前 stdout **精确键名**，可直接用于 `rg`。其中 transaction、commit、beat、
line 和 byte 是不同统计单位，不能仅按名称相近而互换。

| 精确字段 | 解释 |

## 7. 轨迹、镜像和热图文件

文件必须由本次运行的对应导出选项生成；只有 result.json 并不会自动产生下列文件。

### 7.1 Host 与 Transaction 响应 CSV

Host CSV 是完整请求完成视图；Transaction CSV 是拆分后的 DRAM 事务完成视图。
一个 Host 请求可以对应多条 Transaction，不应按 CSV 行号一一配对，应按 host_request_id 关联。

| 字段 | 文件与含义 |
|---|---|
| host_request_id | 两种文件的聚合标识；在途 Host ID 必须唯一 |
| request_id | Transaction 的请求 ID；子事务可能共享，不是全局唯一事务编号 |
| transaction_index / transaction_count | 子事务索引 / 该 Host 的子事务总数 |
| type | Read 或 Write；Write 响应是完成确认，不要求回显写入 payload |
| system_address / local_address | 系统地址 / 路由至实例后的局部地址；local_address 在 Transaction 文件中 |
| stack / channel | 完成位置；Host 跨位置聚合时可为 -1，具体位置查 Transaction 行 |
| arrival_cycle | 请求到达时间，模型 tick |
| first_issued_cycle / issued_cycle | Host 首条事务 / 当前事务发射时间 |
| completion_cycle / latency_cycles | 完成时间 / 从到达到完成的差值；Host 以整体完成为准 |
| status | 完成状态，不能只以“有响应”认定数据正确 |
| initialized | 返回数据的整体初始化状态；逐字节情况看 initialized_mask_hex |
| data_hex / initialized_mask_hex | 读回字节 / 初始化标记；无返回数据的写确认通常为空 |
| ECC、forwarded、coalesced 相关列 | 本次响应经历的校验、转发或合并信息，不是额外数据包 |

例如 arrival=33、completion=265，则 latency=232 tick。
transaction_count=2 表示一个 Host 拆成两条事务，不表示数据只有 2 Byte。
CSV 数据列过长时，less 的右侧截断符不是文件里真的缺数据。可按表头定位列，
或只选少数列对齐；不要把截图里错位的值当作真实字段对应关系。

```bash
column -s, -t < outputs/artifacts/host_responses.csv | less -S
head -n 1 outputs/artifacts/host_responses.csv
```

### 7.2 命令、DFI 与 Timing 表

| 文件 | 一行代表什么 | 检查方法 |
|---|---|---|
| commands.csv | 一条已发射 DRAM 命令及 cycle、地址层级、请求关联 | 按 stack/channel/PC/SID/bank 分组，看 ACT、列命令、PRE、维护间隔 |
| DFI event CSV | 抽象 PHY 的命令/数据事件、beat 或信号状态 | 对照事件类型、关联请求、数据与初始化掩码；不是真实电气波形 |
| timing.csv | 某标准某个 Timing 的有效 nCK 数值及来源、是否要求 vendor、是否被覆盖、依据备注 | 数值正确性与来源完整性分开检查 |

Timing 行最后的 `""` 表示 reference/备注为空，不是前面的 Timing 数值丢失。
`derived` 说明程序按关系生成；是否足以用于目标器件，需要看其依赖值的来源。
来源分级和严格检查边界见[审计](审计.md#provenance)。

### 7.3 最终镜像、初始化与持久文件

final.txt 是带键名的镜像文本；final.csv 是同一已分配数据集合的表格视图，
并非把未访问的整颗 DRAM 全部展开。两者可以记录比 Host 行更细的后端行。

| final.csv 字段 | 含义 |
|---|---|
| address / data | 后端行地址 / 实际字节序列；每两个十六进制字符是一个 Byte |
| init / initialized | 逐字节初始化标记 / 整行初始化状态；ff 是该字节已初始化，不是 payload=ff |
| version | 该行更新版本计数，不是仿真 cycle |
| last_writer / last_write_cycle | 最近写请求标识 / 最近写完成记账时间 |
| checksum | 数据校验值，不是存储地址 |
| ecc_valid / ecc_hamming / ecc_overall / ecc_uncorrectable | ECC 校验信息及不可纠正状态；不是厂商完整 on-die ECC 实现 |
| channel / pseudo_channel / sid / rank / bank_group / bank / row / column | 逻辑地址解码结果 |
| stack / die / layer / tile_* / floorplan_* | 当前研究拓扑映射结果，不等于厂商版图坐标 |
| thermal_* / subarray / mat_* / cell_* / microbump_* | 热网格及细化研究坐标；计算和局限见项目指南 |

mismatch.txt 保存实际检测到的不匹配及其上下文；零记录仅在确实执行检查后才有意义。
golden 比较要使用相同请求、种子、mask、初始化规则和地址映射。顺序编号、时间和研究坐标
不是原始 payload；不能仅凭两个 CSV 文本不同就判定数据后端错误。

data.bin 保存 payload，.init/.meta/.present 保存初始化位、元数据与存在/写入位。
文件布局及持久性保证由[项目指南后端章节](项目指南.md#backends)解释。
`ls -lh` 的大小是逻辑长度；`du -h` 是文件系统实际分配量；后者不应拿来替代模型容量。
`stat` 的 allocated_blocks × block_bytes 才是该文件已分配字节数。

### 7.4 热图和可视化阅读

热图显示 thermal grid 的温度，坐标不是 tile_x/tile_y，也不是以微米计的物理位置。
颜色对应节点绝对温度；跨图比较先检查色标范围是否一致。只生成了被事件或耦合触达的
稀疏节点，所以空白区表示没有导出节点，不表示 0°C；HBM 与 LPDDR 图块覆盖范围不同
可以来自组织、层映射、地址流和触达范围不同，不能直接判断协议实现有误。

热图文本末列 `address_kind` 区分 `direct_event`（有直接事件的代表地址）和
`coupling_only`（仅被热耦合触达）。后者的 `ch/pc/sid/rank/bg/bank/row/col`
等无法确定的 DRAM 地址字段为 -1，但 thermal/tile/grid 坐标仍是该节点的真实模型坐标。
`events=0` 的节点也可能已被邻居加热。即使是 `direct_event`，代表地址也不是节点的
唯一来源：热节点 key 不含 Channel，多个地址可汇入同一个节点。

生成原理、能量方程、坐标公式见[项目指南热模型](项目指南.md#thermal)。
可视化中时间线按 lane 分组，过滤条件会隐藏其他命令；采样图用于浏览，

## 8. 性能分析方法

### 8.1 先判断结果能否比较

先按第 4 节排除 failed/truncated、未排空工作和数据错误，再固定协议、模型参数、
地址空间、请求粒度、读写比、调度、后端及随机种子。保留 resolved.cfg 和 result.json。
运行时间长短是宿主性能，不是 DRAM 延迟；打印间隔不会改变模拟时间。

每个指标只回答一个问题：

- 吞吐量：单位模拟时间完成多少有效数据。
- 读事务延迟：单条完成读事务平均等了多久。
- 行命中率：调度首次分类时的局部性。
- 队列与反压：等待发生在哪一层。
- 能量和温度：当前参数化模型的代价，不是实际器件测量。

行命中率为 0 不必然是错误。以主模板 HBM4 的默认顺序流、64 B Host/32 B 事务和
XOR Channel 路由为例，1024 个 Host 请求拆成 2048 个事务，其
`(Channel, PC, SID, BG, bank, row)` 组合全部不同，不能复用已打开行。
统计时不能漏掉 Channel：不含它时只剩 64 个不同组合，会错误预测复用。
2048 个 Host 请求开始产生地址复用，但首次调度行命中还受刷新、排队和行政策影响；
几何推导的复用率不等于必须达到的命中率，不应将某次约 46.73% 的结果作为所有配置的阈值。

### 8.2 带宽、延迟和功耗的关系

```text
t_ns = system_cycles × tick_duration_ps / 1000
BW_GBps = (read_bytes + write_bytes) / t_ns
Peak_GBps = data_rate_mbps × data_bus_bits / 8000 × 实际建模实例数
Utilization_% = 100 × BW_GBps / Peak_GBps
P_mean_W = energy_pJ / t_ns × 0.001
```

例：完成 32,768 Byte、模型时间 4,096 ns，则带宽为 8 GB/s。
这是演算示例，不是固定的 HBM4 验收结果。改变请求数、Timing、PHY、刷新或注入方式，
system_cycles 就会变化，不应要求复现某一截图中的 cycle 数。

这里 Peak 是接口理论峰值；协议空隙、方向切换、激活、刷新和有效载荷损耗使实测较低。
HBM 多 Stack 使用并行的系统时间作分母，不把各控制器时间相加。
单控制器验证口径不能套完整 Stack 数的峰值公式，应使用本次实际生效的 peak 输出。
平均延迟不能对每个 Stack 的均值直接做算术平均，应按完成读数加权；
吞吐可以在相同模拟窗口内求和。

### 8.3 注入率—延迟—吞吐曲线

扫描 inject_interval 时，其倒数描述待注入 Host 请求的供给率（每 tick）；
发生反压时，实际接受率会更低。Host 拆分粒度改变后，相同 Host 率不等于相同 DRAM 事务率。
跨频率比较若目标是相同物理负载，应固定 requests/ns，而不是只固定 requests/tick。

```bash
mkdir -p outputs/performance
python3 tools/performance_curve.py --binary ./build-clang-debug/hbm_sim \
  --standards hbm4 --requests 512 --intervals 16,8,4,2,1 --read-ratios 100,50 \
  --csv-out outputs/performance/curve.csv --json-out outputs/performance/curve.json
```

低负载时延迟接近固定服务开销；继续加压时吞吐上升，随后在瓶颈处饱和，
排队延迟和反压增加。若吞吐低且延迟很高，依次查看地址分布、行冲突、读写换向、
刷新/RFM、PHY 和入口队列，不应先放大所有 buffer。
实线与虚线如分别使用吞吐、延迟两套纵轴，必须按各自单位读取。

### 8.4 多 Stack、后端和参数实验

比较多 Stack 时分清“固定系统总负载”和“固定每 Stack 负载”；增加实例但请求
仍集中于一个 Stack，不会自动获得线性带宽。查看分 Stack 完成量和带宽确认分布。

后端 sparse/mmap_sparse/chunk_file 改的是宿主数据保存方式，不应凭宿主耗时推断
模型内 DRAM 性能变快。相同实验应先验证最终 payload/初始化结果一致，再比较 RSS、
磁盘分配和宿主运行耗时。缓存项数不等于 DRAM bank 数。

[architecture_sweep](../experiments/architecture_sweep/README.md) 将多个架构用例分别运行，
汇总 results.csv；每行是一种配置/负载组合，不是一条访存请求。
身份列用于分组，完成/检查列用于筛选有效实验，时间/带宽/延迟列沿用本文口径，
相对变化必须选择明确基线。运行命令见项目指南测试章节。

参数敏感性应一次控制少量变量；不确定性区间来自实际采用的参数区间、分布和样本，
不是自动得到的厂商误差界。没有校准依据时，标为探索区间，不称置信度认证。
